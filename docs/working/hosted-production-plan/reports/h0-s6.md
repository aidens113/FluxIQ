# H0-S6: IAM decision volume from panel polling, audit cost, list-filter cost

Tree: `fxwork/t782/!FluxIQ` (branch task/t782-hosted-h0-spikes). Scripts: `spikes/h0-s6/{bench-sqlite,bench-filter,volume}.cjs`.
Machine: Windows 10, Node 22.23, sqlite3 3.52.0 (Core's `sqlite3@6.0.1`), scratch file under the session scratchpad.

## Question
How many IAM decisions does one open panel tab generate, what does recording every one cost in rows and bytes
over 90 days, and what does per-item list filtering cost?

## Method
1. Static inventory of timers and fetch loops in `apps/web/src` (paths below relative to it), with steady-state arithmetic.
   One decision per `/api/programs/[programId]/[endpoint]` call (goes to `GlobalProgramApiRegistry.call`) and one per
   `/api/client-gateway/snapshot` call; plus one per returned item for list endpoints once filtered by `Read`.
2. `node spikes/h0-s6/bench-sqlite.cjs`: SQLite insert throughput and bytes per row. `node spikes/h0-s6/volume.cjs`: arithmetic.
3. `node spikes/h0-s6/bench-filter.cjs`: stand-in evaluator, 10 statements (3 with an owner or tag condition, 2 wildcard-action,
   2 Deny), regex-compiled wildcards, 80% of items allowed.

## Answer
- Polling makes decisions the dominant audit source: 12 to 156 per minute on Home, 84 per minute in an idle Studio tab, 826 in a live run. A calm day is about 40,000 allow rows per active user, a heavy day about 85,000.
- Stored as the plan's JSON shape this is 450 B/row and 163 GB (100 users, calm) to 3.4 TB (1,000 users, heavy) over 90 days. Stored compactly it is 59 B/row (27 B without secondary indexes): 21 to 45 GB for 100 users, 213 to 449 GB for 1,000, or 213 to 449 MB per user. Compact storage makes recording every allow affordable; the JSON shape does not.
- Insert cost is not the limit if writes are batched. Single autocommit inserts under the default journal (70/s) would saturate a heavy user; WAL with batches of 100+ gives 12,000 to 19,000 rows/s, far above 14 per user.
- Evaluating a list is cheap (about 0.8 µs/item, 8.6 ms for 10,000 items). The audit write dominates when done naively: 56 to 66 µs/item with one awaited statement per row (0.56 s for a 10,000-item list). The buffered path adds nothing measurable (0.74 vs 0.71 µs/item).
- Recommendation: **every per-item filter decision gets its own compact row** (no per-call counts replacing them), written through an in-process buffer and flushed in one transaction; the filter itself never awaits SQLite. Nothing is aggregated away. The full-access fast path is one real decision (an unconditional `Allow *`), so it writes one row naming the list action, the list's scope FRN and `matched` the fast-path statement; that is the decision taken, not a summary of many.

## What it changes in the plan
1. **Row format** (Permissions, "Audit of every decision"): store allows as the compact shape: integer epoch seconds, request id as a per-process counter or 8-byte id, principal/action/resource/matched/origin/ip as ids interned in small dictionary tables (new strings added once). Keep the JSON form only as the export and read format. Index time only on the deny and IAM-change table; allow rows have `time` ordering and a (principal, time) index only if the user-facing "my decisions" view needs it (59 B with indexes, 27 B without; both measured). Partition allows by day (one table or file per day) so 90-day expiry is a drop, not a delete.
2. **Write path**: WAL, `synchronous=NORMAL`, one writer per workspace store, buffered flush every 1 s or 100 rows in one transaction. Denies and IAM changes flush immediately. A crash may lose up to one second of allow rows; state this. Never autocommit per decision on the default journal.
3. **Retention**: keep "allows 90 days"; size it at about 0.2 to 0.45 GB per active user. The Risks "Audit volume" line can now say compact storage is the answer and the plan needs no aggregation.
4. **Polling changes** (cut decisions at the source, listed by size of win): (a) the hidden-tab beat is faster than the visible idle beat (12 vs 6 cycles/min); make it 30 to 60 s or pause as the pairing prompt and operational pages already do. (b) The conversation prompt makes `1 + min(N,12)` calls per cycle; replace it with one server-side "pending asks" read: Home with 3 open falls from 48 to about 12 decisions/min. (c) Gate `useRunControl` (1.5 s) and the Clients view (5 s) on visibility. (d) Merge the pairing snapshot and prompt into one inbox call. Together an idle Studio or Home tab would land near 12 to 30 decisions/min, a 3x to 7x cut, but the audit must be sized without these cuts in case they slip.
5. **List-filter rule**: filter with one compiled evaluator per request; skip per-item checks on the full-access fast path (one row); otherwise evaluate every item and write one buffered row per item. Cap list pages (Studio uses 25 and 50) so a filtered page stays under about 100 items; a 10,000-item list is 8.6 ms to evaluate and, buffered, adds about 590 KB of rows.
6. **Parity test**: add the polling call counts above (12 requests/min on Home idle) to the IAM switch's overhead check so a new poller shows up in review.

## Not verified
- Request rates are computed from timer constants in source, not measured in a browser. N (open conversations) and items listed are assumptions (0 to 12, 10).
- Real policy sets will be larger than 10 statements; the evaluator is a regex stand-in, not Core's. Condition-heavy sets will cost more per item.
- The row-per-item SQLite figure (56 to 66 µs) uses one `run` per row on the async sqlite3 driver; a multi-row `INSERT ... VALUES` or the buffered path will be much lower. It shows the naive cost, not the floor.
- Compressibility of allow rows (daily segment plus gzip or zstd, delta times) was not measured; polling rows are highly repetitive, so another large cut is likely.
- Single machine, local NVMe/SSD, no concurrent readers; fsync costs on a hosted disk will differ (the 14 ms autocommit figure is machine-specific).
- Multi-tab or multi-window use multiplies the rates linearly; not modelled.
