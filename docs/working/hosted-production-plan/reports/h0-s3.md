# H0-S3: cost of one Core workspace instance, and whether eviction frees it

Spike on tree `fxwork/t782/!FluxIQ` (branch task/t782-hosted-h0-spikes), Node 22.23.3, Windows, built `dist` (newer than src).
Scripts: `spikes/h0-s3/measure.mjs`, `retain.mjs`, `snap.mjs` (throwaway, in TC).

## Question
How much memory and start time does one workspace instance cost (to size the workspace manager's LRU cap), and does closing it give the memory back?

## Method
`measure.mjs` mirrors `apps/web/src/lib/fluxiq.ts` minus Next: `FluxIQ.create({rootDir, modelProvidersEnabled:false, loadEnv:false})`
then `inspectStorage()` + `setup()` on a fresh scratch root (exactly `initializeFluxIQWebStorage`). The web WebSocket listener
(`startClientGatewayWebSocketServer`) is not started (no ports); the `ClientGatewayService` itself is built inside `create`
(`programs.clientGateway`) so it is included. No host module (none needed). N = 1, 2, 5, 10 instances kept alive in one process,
gc x3 before each reading, 3 repetitions in fresh processes, medians. "Seeded" = after setup, 5 `automationStudio.createProject`
calls plus a `nativeRuntimeSummary` read per instance (the only provider-free seeding used; no Flows, no Lab data).
Free memory stayed above 890 MB at every step (min 893 MB while other agents ran), so no early stop.

Command: `cd spikes/h0-s3 && for r in 1 2 3; do node --expose-gc measure.mjs plain; node --expose-gc measure.mjs seeded; done`

|---|---|---|---|---|

Nothing was reclaimed, all 3 runs, both modes. `close()` reported no errors. `retain.mjs` (4 instances, closed or not, out of scope,
gc): 4/4 still alive; process listener counts unchanged (no SIGINT/SIGTERM hooks come from Core; those are in `fluxiq.ts`).

Retainer, from a V8 heap snapshot (`snap.mjs`), shortest path from the GC roots to a closed, unreferenced `FluxIQ`:
`ModuleWrap (SourceTextModule) -> module-level AutomationStudioActivityHub -> .listeners (Set) -> closure -> context.docs ->
DocsService -> .generators (Map) -> generate closure -> context.providers.domains closure -> context.this -> FluxIQ`.
That is, a process-wide activity hub subscription made during `create` (via `registerHostDocumentationGenerators` /
the hub listener, not removed by `close()`) pins the whole instance and everything it references.

## Answer
1. Idle instance cost is tiny: about 0.5 MB heap, about 0.1 MB RSS, 10 ms warm `create`, 3 - 18 ms `setup`, no timers, watchers,
   intervals or SQLite handles open at rest (handles 0 at N = 10; SQLite is opened lazily, per operation, and kept only while a run
   holds `programStateConnections`). The fixed costs are per process, not per workspace: about 85 MB RSS and a 3.5 - 7 s cold module
   load, paid once.
2. Eviction does not give memory back today. `close()` releases handles and pools but the instance stays reachable through the
   module-level activity hub listener set. With an LRU manager, evicted workspaces would leak about 0.5 MB each when idle and
   far more for a workspace that had run builds (caches, stores), and an evicted workspace keeps receiving hub events.
3. Two further process-wide singletons affect isolation, not memory: `programStateConnections` (module-level SQLite pool) is
   `closeAll()`ed by every instance's `close()`, so evicting workspace A closes connections kept by workspace B's in-flight run;
   and the activity hub is shared by all instances in the process (cross-workspace event fan-out until S4's per-workspace
   hub lands).
4. Not measured: memory of a workspace actively building or running (Flow graphs, run event buffers, model-context caches). That
   dominates real cost and needs its own measurement under H1 with a mock provider.

## Recommended LRU cap (16 GB / 4 vCPU VM)
Idle memory is not the constraint, so the cap is a safety bound plus a handle/fd bound, not a RAM fit.
- Budget: 16 GB less OS and services 2 GB, Node base plus web app and module graph about 0.5 GB, headroom 25 % of the rest (3.4 GB)
  leaves about 10 GB for workspace state.
- Measured idle cost 0.5 MB; assume 25 MB per workspace that has been used (50x idle, an assumption until the active measurement
  exists) -> 10 GB / 25 MB = 400 by memory.
- Handles: each used workspace may hold several SQLite files; at an assumed 10 fds each, 200 workspaces is 2000 fds, inside a
  raised `ulimit -n` of 65535 but not worth more.
- Concurrency: 4 vCPU supports about 4 - 8 concurrent builds regardless of cap; that is a separate run-admission limit, not the LRU.
Recommendation: LRU cap 100 workspaces, idle eviction 15 min, as configurable `FLUXIQ_WORKSPACE_CACHE_MAX` (default 100); revisit
after the active-workload measurement. Never evict a workspace with a run, build or open gateway socket in flight.
Eviction is only meaningful once item "Eviction work" below is done; until then the cap bounds nothing.

## What it changes in the plan
- Workspace manager cap: 100 (configurable), not a RAM-derived number; add "pinned while busy" to the manager contract.
- Eviction work needed in Core before H1 (small, bounded): (a) make the activity-hub subscription disposable and have
  `FluxIQ.close()` call it (or scope the hub per instance, which S4 already lists as a per-workspace singleton); (b) scope
  `programStateConnections` per instance instead of module-level so one workspace's `close()` cannot affect another's runs;
  (c) add a leak test: create, close, drop, gc, assert the WeakRef is cleared (the `retain.mjs` check is the template).
- "Split runtime from storage" is not needed: instances are cheap enough to keep in-process; the fix is disposal, not a new process.
- Add the cold module-load figure (3.5 - 7 s) to the H1 startup budget: workspace creation after the first costs about 30 ms, so
  workspace cold start is not a user-visible problem.

## Not verified
Active-run memory; behaviour with a real domain/host module registered (adds per-instance registrations); Windows vs the Linux VM
(RSS accounting and fd limits differ); a heap-retention check after fixing the hub; seeded workspaces with Flows, runs or
recordings (only 5 empty projects were created); the WebSocket listener's own cost.
