## Answers and the plan changes they force

**S1 (= D0), sign-in tab flow: passes.**
- What passed:
  - Flow A completes, with the extension observing `/connect/done`, on Chrome 156, Edge 156 and Playwright's Firefox 1475 (an add-on installed temporarily over the remote debugging protocol, RDP).
  - The worker woke after a forced stop and accepted the sign-in. On Chrome and Edge this showed as 0 service-worker targets, then a new boot id. On Firefox the event page reloaded with a new boot id.
  - The pending record survived in `storage.session`.
  - The welcome-tab case (a tab the extension did not open) is accepted.
  - Wrong state, wrong origin (`localhost` against `127.0.0.1`) and an expired pending record are all rejected.
- Downstream plan changes:
  - Act on `changeInfo.url` only. The `status:"complete"` event fires a second time and made the first draft double-record.
  - Claim the pending record exactly once.
  - No new permission is needed.
- Side finding: branded Chrome and Edge 156 ignore `--load-extension`. Loading works through `--enable-unsafe-extension-debugging` with CDP `Extensions.loadUnpacked`. Any branded-browser e2e or Lab path needs this.

**S2, Caddy, `wss` and the private listener: transport proven through a Node TLS proxy stand-in; Caddy itself not run.**
- What works: `wss` reaches `pairing_required`, and web or unlisted Origins get 403.
- Gaps against the plan:
  - (a) When an allowlist is set, a missing Origin is refused. The plan says to allow it, so a decision is needed.
  - (b) There is no `moz-extension://*` matching, only exact strings. Firefox IDs are generated per install, so this needs prefix matching.
  - (c) There is no frame cap (a 20 MiB frame was accepted), no hello deadline and no rate limit.
  - (d) The gateway never sees the client IP or `X-Forwarded-For`.
  - (e) With no allowlist set, every Origin is allowed. Public profiles must refuse to start without one.
- Lane A must own (a) to (e).
- A Caddyfile draft and its validate commands are in `spikes/h0-s2/`.

**S3, instance memory and start time: instances are cheap; eviction leaks.**
- Cost: an idle instance is about 0.5 MB of heap and takes about 10 ms to create warm. The fixed cost is per process: 85 MB of resident memory and a 3.5 to 7 s cold module load.
- The leak: after `close()`, 10 of 10 instances stay reachable. The module-level `AutomationStudioActivityHub.listeners` holds each one. My re-run of `retain.mjs` showed `alive:[true,true,true,true]`.
- Coupling between workspaces: closing any instance runs `closeAll()` on the module-level `programStateConnections` pool, so closing one workspace closes the connections of every other.
- Plan change (lane C):
  - The LRU cap becomes 100, configurable. This is a safety bound, not a memory fit.
  - Pin a workspace while it is busy.
  - Three Core fixes come before eviction: make the hub subscription disposable, give each instance its own `programStateConnections`, and add a leak test.
  - Splitting runtime from storage is not needed.

**S4, global-instance callers and singletons:**
- 31 direct call sites in 22 files, plus 17 indirect calls through `lib/auth.ts`.
- Lane C2 gets 5 batches covering 18 files. C1 owns `lib/fluxiq.ts`, `lib/auth.ts` and `instrumentation.ts`.
- The plan's singletons, checked:
  - Confirmed: `automationStudioContexts`, the activity hub and the host-lease scope.
  - Corrected: the step-log directory is an environment variable plus path caches that never evict.
  - Missed by the plan: the gateway-trace and offline-trial `installed` singletons, the login `trackers` map, and the `FLUXIQ_PUBLIC_CLIENT_WS_URL` environment write.
- Leak: `getFluxIQWebRuntimeStatus` exposes `hostRoot` and `fluxiqDir`; omit them under `service`.
- Six design decisions (D1 to D6) are in `h0-s4.md`. The main one is that callers without a `Request` need `workspaceFluxIQ` to accept headers or cookies.

**S5, key release for extension-started builds: the plan's design does not hold as written.**
- `approvingSessionId` cannot be the key handle. The approving session expires within 12 hours, while the browser credential lasts 60 days.
- It is also the raw cookie value, so it must never travel in `runContext`.
- Today:
  - A build pins one session for every call, and a logout during a build fails it.
  - `session-key.ts` picks the newest key of anyone in the workspace. This is a denial, not a leak: the probe refused user A while A's own key was unlocked.
  - An administrator revoking a session does not drop its unlock.
  - `close()`, and so idle eviction, revokes every unlock in the workspace.
- Plan changes:
  - Rewrite Core plan line 595 to say: resolve the user's live unlock in this workspace on each call; otherwise raise a typed `secrets.locked` error.
  - Lane D: `approvingSessionId` and `startedFromSessionId` become digests used for audit only.
  - B1 selection fix: use the Flow's key, else the caller's own key, after a `UseKey` check.
  - Admin revoke calls `revokeSessionUnlock`.
  - Lane C: either move `HeldKeys` out of the instance, or never evict a workspace that holds an unlock, a socket or a run.
  - N4: one message for a locked key, and re-unlock without signing out.

**S6, audit volume and list-filter cost: affordable only if stored compactly.**
- Decision rates: an idle Home tab makes about 48 decisions a minute, an idle Studio tab 84, and a live run 826. That is 40,000 to 85,000 allow rows per user per day.
- Storage: the plan's JSON row is about 450 B, which comes to 163 GB to 3.4 TB over 90 days. A compact row with interned ids is 59 B, or 0.2 to 0.45 GB per user.
- Evaluation cost: about 0.5 to 0.8 µs per item.
- Write cost:
  - My re-run measured 32 to 46 µs per item to write per-item rows to SQLite, even in one transaction per list. Audit writes must therefore stay off the request path.
  - Plan change (lane B2): an in-memory buffer flushed asynchronously in batches (WAL mode, every 1 s or 100 rows). Denies and IAM changes flush immediately.
- Other plan changes:
  - Allow rows are partitioned by day.
  - Every per-item decision keeps its own row, and nothing is aggregated.
  - Recommended polling cuts: the hidden-tab beat is currently faster than the visible one; the conversation prompt makes up to 12 detail reads per cycle; run control and the Clients view are not gated on visibility.
