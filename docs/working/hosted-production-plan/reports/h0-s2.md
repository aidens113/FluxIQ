# H0-S2: Caddy carrying wss to the client gateway

## Question
Can a TLS-terminating reverse proxy carry `wss` to Core's client gateway (plain ws) with the
plan's origin rules, and keep the provisioning listener private? Plus three open items.

## Method
Tree TC = fxwork/t782/!FluxIQ. Caddy was not available, so a Node `https` server (self-signed
cert, 127.0.0.1:47202) forwarded Upgrade requests to the real gateway
(`startClientGatewayWebSocketServer`, bundled with esbuild from source, 127.0.0.1:47201, fresh
in-memory `ClientGatewayService`), adding `X-Forwarded-For` / `-Proto` as Caddy would. A raw TLS
WebSocket client set Origin freely (Node's global WebSocket cannot). Harness:
`TC/spikes/h0-s2/run.mjs` (`node run.mjs open|list [idle]`). All processes exited on their own;
the temporary node_modules junctions I made were removed (real node_modules verified intact).

## Evidence
Tooling: `where caddy` -> "INFO: Could not find files"; `where docker` -> same;
`where winget` -> `...\WindowsApps\winget.exe` (present, unused).

Through the proxy over wss, gateway started with no allowedOrigins ("open") and with an
allowlist (`chrome-extension://abc...` + `https://app.getfluxiq.com`) ("list"):

| Origin | open | list |
| --- | --- | --- |
| none | 101, `server.pairing_required` | **403** |
| https://evil.example | 101, pairing_required | 403 |
| listed chrome-extension://... | 101, pairing_required | 101, pairing_required |
| other chrome-extension://... | 101 | 403 |
| moz-extension://1234-5678 | 101 | 403 (no wildcard support) |
| https://app.getfluxiq.com | 101 | 101 |
Direct plain-ws control with evil Origin: open 101, list 403 (proxy changes nothing).

- Hello without a credential reaches `server.pairing_required` ("Approve this client in FluxIQ
  before sending data."): confirmed, over wss.
- Oversized frame (open mode): a 20 MiB text frame is accepted, parsed, answered with
  `server.error` ("Unexpected token 'a'...") and the socket stays open; RSS rose ~122 MiB.
  A frame header claiming 1 GiB followed by 48 MiB of payload: socket stays open, bytes buffered.
  Source: `readFrame` only rejects lengths > MAX_SAFE_INTEGER; `acceptData` does
  `Buffer.concat` with no cap. **No frame or buffer limit exists today.**
- Hello timeout: an idle connection with no hello was still open after 13 s. **No hello deadline.**
- Client IP: the gateway's upgrade request showed `remoteAddress: 127.0.0.1` (the proxy), with
  `x-forwarded-for: 127.0.0.1`, `x-forwarded-proto: https`, `host: app.getfluxiq.com` present as
  headers. But `acceptClientGatewaySocket` / `gateway.connect({socket})` never read either, so
  the session carries no client IP at all today (grep: no `remoteAddress`/`x-forwarded` in
  `apps/web/src/server` or `packages/fluxiq/src/client-gateway`, outside tests).
- Proxy dependencies: none on Host (not checked). The only loopback check is at startup on the
  *bind* host (`isLoopbackHost(host)`), which forces a restrictive allowlist off loopback; it does
  not look at request Host/peer. A proxy that passes Origin and Upgrade/Connection/Sec-WebSocket-*
  unchanged is all it needs.

## Answer
Yes at the transport level: wss to plain ws works, pairing_required is reached, and Origin
filtering works through a proxy because the Origin header passes untouched. Four gaps versus
`hosted-production-plan.md` 487-507:
1. **Missing Origin is refused when an allowlist is set** (`isOriginAllowed`: `if (!origin) return false`),
   the opposite of the plan's "a missing Origin is allowed". Code and plan must be reconciled; the
   existing unit test pins the refusal. Pairing-credential auth makes allowing it safe, but it is a change.
2. `moz-extension://*` wildcard is unsupported (exact string match only); Firefox IDs are per-install UUIDs, so the plan's default needs prefix matching.
3. Limits (16 MiB frame, 10 s hello, rate limits) are all unimplemented.
4. Client IP is not captured; `FLUXIQ_TRUST_PROXY` needs real plumbing (peer address + XFF into the session/audit).
Also: no allowlist means everything is allowed (including evil web origins); the hosted profile must always set one.

**b. When does the Chrome Web Store assign the item ID?** Not stated in the pages I could read.
developer.chrome.com/docs/webstore/publish: "Once you've uploaded your extension, you will see it
as an item in the dashboard." developer.chrome.com/docs/extensions/reference/manifest/key: upload
the package "to the Chrome Developer Dashboard without publishing it", copy the public key from the
Package tab into manifest `key`; "This way the extension will use the same ID", then compare with
"the Item ID in the Developer Dashboard". Inference (not quoted): the ID exists once the first draft
is uploaded, before publishing; and `key` pins it. Unproven: whether it exists earlier (item created
without upload).

**c. Does Next serve `app/.well-known/...` directly?** Next 15.5.24. The official project-structure
docs (nextjs.org/docs/app/getting-started/project-structure) say folders define segments, "a route
is **not publicly accessible** until a `page.js` or `route.js` file is added", and only `_folder`
(private) and `(group)` / `@slot` prefixes are special; dot-prefixed folders are not mentioned.
By those rules `app/.well-known/fluxiq/route.ts` should route, but no doc confirms it. My test
failed to run: webpack dev rejects any path containing `!` (the checkout is `!FluxIQ`; "contains
exclamation mark (!) ... reserved for loader syntax"), and turbopack rejected the junctioned
node_modules. Inconclusive; the rewrite in `next.config.ts` (plan line 419) stays the safe choice.
Side finding: `next dev` with webpack cannot run from a path containing `!`.

## Still unproven without Caddy
Caddy's actual WebSocket handling (Upgrade pass-through, `stream_timeout`, close delay), the
Caddyfile syntax and directive names, automatic TLS, and whether `header_up` replaces a client-sent XFF.

## What it changes in the plan
- Add work items: frame/buffer cap, hello deadline, rate limits (all absent), peer-IP/XFF plumbing into sessions and audit.
- Decide missing-Origin: change code to allow it (plan) or change the plan.
- Origin matcher needs prefix/wildcard for `moz-extension://*`.
- Hosted gateway must refuse to start without an allowlist (open mode admits any web Origin).
- Keep the `/.well-known` rewrite; do not rely on a dot folder until tested from a path without `!`.
