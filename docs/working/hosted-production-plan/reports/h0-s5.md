# H0-S5: how an extension-started build reaches a model key

Worker: worker-heavy (spike H0-S5), 2026-10-28. Trees: TC/TE at `fxwork/t782` (task/t782-hosted-h0-spikes).
Paths below are relative to TC (`packages/fluxiq/src/...` shortened to `src/...`) unless they say TE.

## Outcome

Short answer: the plan's design needs changes. The key is already released only to the
browser owner's own unlock, so it does not leak, but three defects remain:
1. **Wrong key picked (a denial, not a leak).** `session-key.ts` picks the newest DeepSeek key
   of anyone in the workspace. Any member whose key is not the newest is refused, even while
   their own key is unlocked.
2. **Pinning to `approvingSessionId` would be a step backwards.** Today the browser is mapped to
   the user's newest-expiring live unlock, not to the approving session. A pinned approving
   session would die within 12 hours, while the browser credential lasts 60 days.
3. **A 15-minute workspace eviction would drop every unlock.** That includes the unlocks of
   users whose panel cookie is still valid.

## Method

I traced the code statically from the extension's relay to the key release. I then wrote and
ran a probe test with no model provider: `spikes/h0-s5/selection.test.ts`. It uses the real
`SecretKeysService` in memory, weak scrypt and fake key strings, with no network.

Command, run from TC/packages/fluxiq:
`npx vitest run --dir ../../spikes/h0-s5 --reporter=verbose` -> `Test Files 1 passed (1), Tests 3 passed (3)`, 1.67s.

## 1. From the chat message to the key release, hop by hop

| Web route | The token resolves to a ready gateway session bound to the trusted client. | `apps/web/src/app/api/programs/[programId]/[endpoint]/route.ts:96-107`; `src/client-gateway/service/access.ts:53-64` |

**Is there a "first unlocked key of anyone" fallback?** Partly. The code picks the newest key of
anyone, and the release then refuses any key that is not the caller's. So nothing leaks, but a
member can be locked out of their own key (probe line 2). The chat model uses the same function
(`.../llm/deepseek/panel-command-key.ts:20`). The plan's B1 fix is still needed. The bug is a
denial plus the ignored Flow key, not a disclosure.

Two related findings:
- Runs started from the extension's "Run it" are mapped the same way
  (`api/handlers/runtime-execution.ts:79-80`).
- `sealedFor` unlocks v1 or unstamped records for any user (`secret-keys/runtime/key-store.ts:55`).
  Only the original password opens them, so this does not leak either.

## 2. Where unlocked keys live, and when they are dropped

- **Scope.** Unlocked keys live in process memory, one `HeldKeys` per `SecretKeysService`. It is
  a private field (`service.ts:95`), holding two `Map`s (`held-keys.ts:33-35`). There is one
  service per `createGlobalProgramRuntime`, which means one per FluxIQ instance
  (`_shared/runtime.ts:46`). Unlocks are keyed by the raw identity session id. That id is the
  cookie value itself (`apps/web/src/app/api/auth/login/route.ts:97-102,119`).
- **Created** at panel sign-in (`login/route.ts:97`), and by a key create or rotate on a session
  that has not been unlocked yet (`service.ts:438-463`).
- **Dropped when:**
  - the session's expiry timer fires (`service.ts:287`; sessions last 12 hours,
    `identity-access/runtime/service.ts:51`);
  - the user logs out (`apps/web/src/app/api/auth/logout/route.ts:11`);
  - the key is rotated, edited or deleted (`held-keys.ts:93-128`);
  - `FluxIQ.close()` runs, which calls `secretKeys.close()` and then `revokeAll()`
    (`src/framework/index.ts:209`; `service.ts:424-427`);
  - the process restarts, because nothing is persisted.
- **Gap.** An administrator's `identity-access revokeSession` deletes the identity session but
  **not** its unlock (`identity-access/api/handlers.ts:201-212`;
  `identity-access/runtime/service.ts:381-388`). `unlockedSessionFor` keeps handing that unlock
  to the user's browser until the 12-hour timer fires.
- **Sessions survive a restart; unlocks do not.** Identity sessions are stored in a repository,
  so a cookie stays valid after a restart while its keys are locked.
- **What the gateway can see.** When a browser connects, the gateway knows only its own
  `sessionId` and `operatorUserId`. It has no identity session id.

## 3. Does `approvingSessionId` suffice? No, not as the key handle.

| Case | Today | Pinned to `approvingSessionId` | What the user sees |
| --- | --- | --- | --- |
| The approving session logs out or expires while the browser stays connected | New messages fall back to another live unlock of the same user (probe, test 2). A build already running stays pinned to the session it resolved and fails on its next call (probe: `call 2 ... refused`). | Locked, even while the user has another unlocked session. Every browser stops after at most 12 hours, but the credential lasts 60 days. | Before a build starts: `keyLocked` adds "Your model key is locked for this browser: sign out of FluxIQ and sign in again…" (`.../conversations/commands/progress.ts:59`). Mid-build: the raw message "Secret key session unlock is unavailable" (`service.ts:310,314`). |
| The user has several sessions | The latest expiry is used (`service.ts:412-414`). | Only the approver's session counts. | As above. |
| The workspace instance is evicted after 15 minutes idle (plan line 522) | No eviction exists yet. Under the plan, `close()` would revoke every unlock in the workspace (`framework/index.ts:209`), and the gateway, which is part of the instance, would drop the socket. | The same: the held keys go with the instance. | The panel cookie is still valid, but builds lock with the raw or sign-out message. The user is not prompted to sign in, because the cookie still works. |
| Server restart | Everything is locked (process memory). | The same. | This is N4. Today's wording is the progress.ts:59 sentence, not the plan's N4 sentence. |
| Another user's browser in the same workspace | It acts as its own approver (`program-route.ts:187-194`) and never reaches another user's unlock (`service.ts:408-416`; probe B line). | The same. | B stays `keyLocked` until B signs in. With today's selection bug, B is also refused whenever A's key is newer. |

## 4. The minimal contract change

- **Credential (lane D).** Keep `approvingSessionId` as an **audit field only**. Store a digest
  of it, never the raw value, because the raw identity session id is the cookie. Add nothing
  else to resolve keys: `userId` and `workspaceId` are enough.
- **`runContext.startedFromSessionId`.** This field travels to the browser on every action
  command, so it must **not** be the raw identity session id. Use the session digest
  (`identity-access/runtime/session-digest.ts:8`) or the gateway session id. It is for audit
  and correlation only. It is not a key handle.
- **Release by user, call by call.** Replace the build's fixed `caller.actorSessionId` with a
  per-call lookup: the started-from unlock if it is still live, else the user's latest live
  unlock in this workspace (`unlockedSessionFor`), else a typed `secrets.locked` error.
  Functions that change:
  - `session-key-provider.ts:74-86`: take an `unlockedSessionFor` port.
  - `conversations/commands/caller.ts:33-42`: return the user plus a preferred session, not a
    fixed session.
  - `llm-generation.ts:126`.
  - `runtime-execution.ts:80`.
- **Selection fix (B1).** Change `releaseAutomationStudioSessionDeepSeekKey(ports, caller,
  {flowKeyId?})` so that it:
  - uses the Flow's `llmSecretKeyId` when it is set;
  - otherwise picks the newest enabled DeepSeek key whose `createdBy === caller.userId`, or,
    for legacy records without a stamp, one that the caller's unlock actually holds;
  - checks `secrets:UseKey` first;
  - never picks a key the caller cannot open.

  This needs `snapshot` to keep exposing `createdBy`, which it already does (`service.ts:517`).
  The probe's owner-aware branch releases A's own key (`A with owner-aware selection: released
  fake-key-A`).
- **Admin session revoke.** `identity-access` revoke must also call `revokeSessionUnlock`, the
  same way logout does.
- **Eviction rule (lane C).** Either one of these works:
  - Move `HeldKeys` out of the instance into the workspace manager's entry. Inject it into
    `SecretKeysService` through a new constructor option, and have eviction skip `revokeAll`.
    Keep `revokeAll` for a real shutdown or a deletion.
  - Never evict an instance that holds a live unlock, a ready socket, or a running build or run.

  The first is cheaper in memory. Either way, `close()` needs an eviction mode separate from
  its shutdown mode.
- **N4.** Use one typed error, `secrets.locked`, for every path. The message should be the plan's
  "Sign in at app.getfluxiq.com to unlock your model key", replacing both the raw "Secret key
  session unlock is unavailable" and the sign-out sentence. The panel should offer to re-unlock
  with the password, without a sign-out, when the cookie is valid but nothing is unlocked.

## What this changes in the plan

- **B1:** widen the selection fix to owner-aware selection plus the Flow key plus `UseKey`.
- **D:** `approvingSessionId` becomes a digest used for audit only.
  `runContext.startedFromSessionId` becomes a digest or gateway id, never the raw session.
- **C:** held keys must survive idle eviction, or eviction must be blocked while keys are
  unlocked.
- **N4:** one locked-key error, with a prompt to re-unlock.
- **Line 595 of the plan,** "use that session's unlock while it lives", should become "use the
  user's live unlock in this workspace".
