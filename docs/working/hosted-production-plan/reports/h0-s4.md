# H0-S4: call sites of the panel's global Core instance, and per-root singletons

Tree TC = `fxwork/t782/!FluxIQ` (branch task/t782-hosted-h0-spikes). Read-only; nothing in the tree was edited.

## Question

Which files call `getFluxIQ()` (and the other accessors of `globalThis.__fluxiqWebRuntime`), so C2 can migrate
them in parallel batches by file; and which module-level mutable state in `packages/fluxiq/src` and
`apps/web/src` holds per-root data, so C3 knows what goes per workspace.

## Method

rg over `apps/web/src`, `packages/*`, `scripts`, excluding `node_modules`, `dist`, `.next`, tests (unless noted)
and `apps/web/src/features` (browser-only UI state: 21 module `let`s that live in the user's tab, not the
server). Singleton patterns: module-scope `let`/`var`, empty `new Map/Set/WeakMap/WeakSet`, `= []`/`{}`,
`globalThis`, static fields, `setInterval`, `process.once`, import-time `process.env`/`cwd`.

## Evidence

`initializeFluxIQWebRuntime`, `getFluxIQWebRuntimeStatus`, `setAutomationStudioWebContext`,
`reloadFluxIQWebInstance`, `closeFluxIQWebRuntime`, and host-module helpers (`createFluxIQWebInstance`,
`loadFluxIQHostModule`, `applyFluxIQHostModule`, `resolveFluxIQHostModulePath`, `resolveFluxIQWebHostRoot`).

- `rg -c "getFluxIQ\(\)|getFluxIQWebRuntimeStatus\(|setAutomationStudioWebContext\(|reloadFluxIQWebInstance\(|initializeFluxIQWebRuntime\(" apps/web/src --glob '!**/tests/**'`
  gives 31 call sites in 22 files outside `lib/fluxiq.ts`: 24 in 15 route files, 5 in 5 pages, 1 in
  `instrumentation.ts`, 1 in `lib/auth.ts`. `lib/fluxiq.ts` itself has 5 (definitions).
- Other paths to the runtime: none. `rg -l "<accessor names>|__fluxiqWeb" apps packages scripts` outside tests lists
  only those files and `lib/fluxiq.ts`; no direct `globalThis` read elsewhere, no server actions (`rg "use server"`
  empty), nothing in `packages/` or `scripts/`. `server/gateway-runtime/load.ts:4-16` keeps its own
  `__fluxiqGatewayServerModule` (a loaded module path, not per-root).
- Indirect, through `lib/auth.ts` (`rg -c "currentFluxIQUser\(|requireFluxIQUser\(" apps/web/src --glob '!**/tests/**'`):
  10 `requireFluxIQUser` calls in 9 route files and 7 `currentFluxIQUser` calls in 6 page/layout files. They need
  no edit if `auth.ts` resolves the workspace itself.
- Tests importing or mocking `lib/fluxiq` (`rg -l "lib/fluxiq|/fluxiq\"" apps/web/src --glob '**/tests/**'`): 15 files.

## Answer

31 direct call sites in 22 files plus 17 indirect calls through `auth.ts`, in 6 batches (C1 plus B1-B5); C2 is 18 files and
29 calls. Of the plan's four singletons, `automationStudioContexts`, the activity hub and the host-lease scope are confirmed;
"step-log directory" is corrected (a process env var plus path-keyed caches, not a held instance). Missed by the plan:
gateway-trace installation, offline-trial installation, login `trackers`, and the `FLUXIQ_PUBLIC_CLIENT_WS_URL` env write.

## What it changes in the plan

- C2 batch list: use B1-B5 above; C1 owns `lib/fluxiq.ts`, `lib/auth.ts`, `instrumentation.ts`.
- C3 per-workspace list: add gateway-trace installation, offline-trial installation, login `trackers`; make host-lease
  `strictlyHeld` an instance field; per-runtime activity hub; step-log becomes a decision.
- Isolation leak beyond singletons: `getFluxIQWebRuntimeStatus` returns `hostRoot` and `fluxiqDir` absolute paths
  (`lib/fluxiq.ts:51-52`), served by `snapshot` and `[endpoint]/route.ts:165`; omit under `service`.

Design decisions needed:
- D1 Callers with no `Request`. Pages: use `headers()`/`cookies()`, so `workspaceFluxIQ` must accept a header/cookie source
  and not only a `Request`. `lib/auth.ts`: has only the cookie, so it resolves session to workspace via the platform
  session store. `instrumentation.ts`: startup initialises the platform store and the `single` entry only. Login: no
  session yet, resolve through the platform store. Shutdown: close all entries.
- D2 Activity hub per runtime: carry it in the existing `automationStudioActivityStorage` scope, or pass it to emitters.
- D3 Step log: off under `service`, or derive a directory per workspace root; evict the path caches on workspace close.
- D4 Performance metrics: operator-only, or filtered by workspace.
- D5 One shutdown handler for the manager.
- D6 Idle eviction must not fire while a run, build or scheduled task is active in the workspace.
