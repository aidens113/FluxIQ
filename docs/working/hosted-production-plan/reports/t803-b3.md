## Open questions and follow-ups for the lead

1. **Wiring (outside my paths).** `programs/_shared/runtime.ts` (lanes A and C) must pass
   `new GlobalProgramApiRegistry({ identityAccess, iam: { profile, workspaceId, source, audit } })`.
   Until it does, `service` enforcement and the decision audit are inert in the running product.
2. **Contracts regeneration (frozen; your call).** `actions.generated.ts` still has `resourceTypes`
   `["*"]`/`["program"]` and no route sources. Feeding it the declared `resource.types` and H2's
   route actions is a regeneration of generated data, with no schema change.
   - Two `custom` resources declare mixed types (`["*", "project"]`, `["project", "*"]`), which
     the catalog schema refuses (`"*"` must be alone).
   - They must become one type before that regeneration. Proposed: `["project"]`.
3. **Behaviour change on four routes (H2).** On snapshot, trace-artifacts, recordings and the
   token path of state-assets, a paired token whose approving person is gone or disabled is now
   refused 401. Before, any valid token passed. This is the program route's existing rule, but it
   is not strict parity. I kept it as a tightening. Revert if you want strict parity.
4. **Registry API.** `authorize` requires a permission, so H2 passes `programs.read` for routes that
   checked none (`AUTHENTICATED_ONLY`). Making the permission optional would remove that.
5. **Hosted-user gaps.** These are narrowing, never widening, and each needs a per-item filter or a
   narrower resource before the hosted panel offers it:
   - pairing approval, the Studio context, trace upload (no `client` owner resolver), the program
     directory;
   - the workspace-wide studio reads (snapshot, categories, client-gateway lists, recordings across
     projects, signal registries);
   - `revoke-session`, which acts on the workspace because its payload names a session, not a user.
6. **Ownership.**
   - Projects created outside `create-project` (chat, schedules) get the default owner, not their
     creator.
   - H3 tells an unknown project id from a known one by matching two runtime error messages. The
     runtime lane should add a public `service.hasProject(id)`.
   - The store's location is reached through `AutomationStudioGatewayTraceServicePools.of(service)`;
     a public root getter on the service would be sturdier.
   - A deleted project's owner record is left behind; it is never answered.
7. **No fast path on `service`.** The guardrail's `Deny` turns off the full-access shortcut (B2's
   evaluator rule), so hosted lists are decided item by item.
8. **Policy versions.** `FluxIQUserAccess` changed but stays `v1` (B2's known gap: nothing forces a
   bump).
9. **Startup refusal.** Refusing undeclared registrations under public profiles is not built. Only
   the completeness test enforces declarations.
