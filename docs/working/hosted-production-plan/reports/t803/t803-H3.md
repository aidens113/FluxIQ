## Persistence finding

The api layer can reach a durable location without editing runtime or storage, through public
surface only:

- `AutomationStudioService` keeps `projectPaths` and its storage root private, and `service.ts` is
  frozen. When the service creates its per-project database pool, though, it hands the pool to
  `AutomationStudioGatewayTraceServicePools.adopt(this, ...)`
  (`runtime/gateway-trace/wiring/service-pools.ts`, exported from the wiring barrel). This happens
  whenever the service is given `dataDir` or `storageRootDir`.
- `AutomationStudioGatewayTraceServicePools.of(service)?.rootDir` (public `readonly rootDir` on
  `AutomationStudioProjectDatabasePool`, `storage/project/database.ts:66`) is the service's
  Automation Studio data directory, the same `automationDataDir` that holds `projects/`. In the host
  under layout v2 that is `paths.recordings`, which is `<fluxiq>/artifacts/automation-studio`.
- Ownership is one program-state document at `<rootDir>/ownership/projects.json`, written through
  `ProgramJsonStore`. It sits beside `projects/`, never inside a project's directory or database.
  - **Under layout v2** the path maps to an `automation.state` SQLite row (id `ownership/projects`).
    Every change runs in `ProgramJsonStore.transaction(...)`, one SQLite transaction, so concurrent
    writers, including other processes, cannot lose each other's writes.
  - **File-backed** (no v2 config): `ProgramJsonStore.update` under its per-file lock with an
    atomic rename. That is safe within one process, the same guarantee every file-backed
    program-state document has.
- A service with neither `dataDir` nor `storageRootDir` has no pool and keeps its projects in memory.
  Its owners are kept in memory too (`AutomationStudioProjectOwnerMemoryStore`).
- The module imports through the wiring barrel (`runtime/gateway-trace/wiring/index.ts`). The
  structure audit's imports rule refused a direct import of `service-pools.ts`, and the
  import-cycles rule is clean with the barrel.

### Second finding: telling a project from an unknown id

The service has no public lookup that answers "not found" without throwing, and `listProjects`
lists one domain scope at a time. `service-catalog.ts` therefore calls
`service.assertProjectDomainAccess(id, null)`, which gives one of three answers:

- It resolves: the project exists and is global.
- It throws `"Automation Studio project is unavailable in this domain scope."`: the project exists
  in another domain scope.
- It throws a message starting `"Unknown Automation Studio project:"`: the id is unknown.

Every other failure is rethrown. This depends on two runtime error messages. One comes from
`runtime/service.ts` `assertProjectDomainAccess`. The other comes from
`runtime/service/projects/store.ts` `findProjectSummary`. `tests/service-catalog.test.ts` pins both
against a real service, so a reworded message fails there. **The runtime lane should add a public
`hasProject(projectId): Promise<boolean>`** (or a non-throwing `findProjectSummary`) to
`AutomationStudioService` in `runtime/service.ts`. That would replace the message matching. It is a
one-line swap in `service-catalog.ts`.

## What changed and why

- `api/contracts/project.ts`: `AutomationStudioProject.ownerUserId?: string | null`, with a doc
  comment.
  - Absent means the answer did not look the owner up.
  - Null means the project has no owner yet.
- `api/ownership/` (new):
  - `types.ts`: the record (`userId`, `source: "creator" | "default"`, `recordedAt`), the store
    port (`read`, and `change`, an atomic synchronous mutation), the catalog port
    (`hasProject`), the defaults port (`workspaceOwner?`, `users`), and the migration result.
  - `owner-records.ts`: parses a stored document. It refuses a malformed entry rather than dropping
    it, because a dropped record would be re-defaulted to someone else. It reads with own
    properties only and refuses `__proto__` as an id.
  - `memory-store.ts`, `document-store.ts`: the two stores described above.
  - `default-owner.ts`: picks the workspace owner if one is named. Otherwise it picks the first
    enabled user with role `adminRole.id` by `createdAtMs`, with ties broken by id. It returns null
    when there is neither.
  - `migration.ts`: `migrateAutomationStudioProjectOwners({ store, projectIds, defaultOwner, now })`.
    - It is idempotent and never overwrites a recorded owner.
    - It checks again for unowned projects inside the atomic change, so a creator recorded
      concurrently is kept.
    - It asks for the default owner at most once, and only when something is unowned.
    - With no default owner it writes nothing.
    - It returns `{ examined, alreadyOwned, assigned, unassigned, defaultOwner, owners }`.
  - `ownership.ts`: `AutomationStudioProjectOwnership implements ProgramResourceOwnerResolver`.
    - `ownerOf(id)`:
      - An unusable id returns null without asking the catalog.
      - An id that names no project returns null and records nothing. This also covers a deleted
        project whose record lingers.
      - A recorded owner is returned as is.
      - Otherwise the lookup runs the migration for that id first, so no project is ownerless while
        someone exists to own it.
    - `recordOwner(id, userId)`:
      - It requires a known project.
      - It replaces a `default` owner, which covers a list that defaulted the project between its
        creation and the registry's `recordOwner`.
      - Recording the same creator again changes nothing.
      - A different creator throws.
    - `withProjectOwners(projects)` adds `ownerUserId` in one change and keeps order and fields.
    - `migrate(ids)` exposes the migration counts.
  - `service-catalog.ts`: the adapter described above.
  - `ownerships.ts`: `AutomationStudioProjectOwnerships.create(service, identityAccess)`,
    `.of(service)` and `.storeFor(service)`. It keeps one ownership per service in a WeakMap, so
    `projects.ts` can reach it by the service without changing `dependencies.ts`. Default owners
    are read from `identityAccess.snapshot().users`. Without Identity Access there is no default
    owner.
  - `index.ts`: the barrel.
- `api/handlers/register.ts`: one import and one line,
  `registry.registerResourceOwners("project", AutomationStudioProjectOwnerships.create(service, identityAccess))`.

### Integration for the supervisor (`projects.ts`)

`const ownership = AutomationStudioProjectOwnerships.of(service);` returns `undefined` only if the
API was never registered for that service. Then, for list:

`{ ...listed, projects: await ownership.withProjectOwners(listed.projects) }`

`create-project` and `update-project` can wrap their single project the same way:
`(await ownership.withProjectOwners([project]))[0]`.

## Open questions or contradictions found

- **No workspace owner exists in Core today.** Neither Identity Access nor the platform has one, so
  `defaults.workspaceOwner` is an optional port and `ownerships.ts` supplies none. In practice the
  migration gives the first enabled `admin` (on a fresh host, the seeded `admin` user). Whoever adds
  a workspace owner passes it in `AutomationStudioProjectOwnerships.create`.
- **Without Identity Access** (`registerAutomationStudioApi(registry, service)` with no third
  argument, as most handler tests do), there is no default owner. Unowned projects answer null until
  a creator is recorded. That fails closed under owner-conditioned grants.
- **A deleted project's owner record is left in the document.** `ownerOf` never answers it, because
  existence is checked first, and project ids are random UUIDs. A purge on `delete-project` would
  need a `forget(id)` call from `projects.ts`, which I don't own.
- **`recordOwner` throws** when a different creator is recorded for a project that already has one.
  The registry's `_shared/iam/record-created-owner.ts` says "A resolver that throws fails the call",
  so a double-create of one id fails loudly. A project is created once under a random UUID, so this
  should never happen in normal use.
- **Cost per check:** each `ownerOf` reads the project index (cached by file identity on the file
  layout, read every time under SQLite) and the owner document.
