## identity-access choices
- snapshot: `workspace()` (lists every user; no `list` filter added, since the brief says snapshot is workspace-scoped).
- create-user: `workspace()` (the user does not exist yet).
- update-user: `user("id")` (handler reads `payload.id`).
- set-password, set-pin: `user("userId")` (handler reads `payload.userId`; the payload names the target, so not selfUser).
- begin-totp, confirm-totp, disable-totp: `user("userId")` (handlers require a payload `userId`).
- create-session: `user("userId")` (mints a session for the named user).
- unlock-vault: `user("userId")` (the handler requires a payload `userId`; the recheck only binds the caller's credentials).
- lock-vault: `selfUser()` (takes no payload; locks the calling session's vault).
- revoke-session: `workspace()`. It takes a `sessionId` or `sessionDigest`, and the handler cannot tell synchronously whose session that is, so no user ref can be built. Workspace means only an unconditioned grant allows it, which is the safe side. If an owner-conditioned revoke is wanted, it needs a session-owner lookup that is not on this seam.
- No endpoint used `custom`: none has the "self unless an id is given" shape.

## secret-keys choices
- snapshot: `workspace()` plus `list` (items = `payload.keys`, ref = key `id`, replace rebuilds `{...payload, keys: kept}`); default `itemAction` is secrets:Snapshot.
- create-key: `workspace()` plus `creates` returning `{kind:"key", keyId: payload.id}` when the response (a `SecretKeySummary`) holds a string `id`, else null.
- update-key, rotate-key, reveal-key, delete-key: `key("id")` (all read `payload.id`).

## Key owner finding
The service can answer it. `SecretKeySummary.createdBy` is stamped from `request.actor?.userId` in create-key, and `SecretKeysService.getKeySummary(id)` is public. Registered inside `registerSecretKeysApi`:
`registry.registerResourceOwners("key", { ownerOf: async (id) => (await service.getKeySummary(id))?.createdBy ?? null })`.
No `recordOwner` is needed, because `createdBy` is already persisted by createKey. A key with no `createdBy` (created without an actor) has no owner, so owner-conditioned grants fail on it. `registerSecretKeysApi` is called once (`_shared/runtime.ts:222`), so the duplicate-resolver throw cannot trigger from this file. I did not check whether anything else registers a "key" resolver.
