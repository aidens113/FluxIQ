## workspace() that is not a create or list
- performanceMetrics, snapshot (projects.ts): `snapshot` returns the whole program snapshot across projects; it cannot be filtered per item, so workspace-wide content kept on `workspace()`.
- createProjectCategory, updateProjectCategory, deleteProjectCategory, reorderProjectCategories (projects.ts): categories are workspace-level, not owned by one project; no `creates` (category is not an owned kind).
- testFlowMapRouteCondition (router.ts): pure condition evaluation, no project in the payload.
- getReusableLlmContextStatus (caches.ts): pool status, no payload scope.
- inspectStateDiff, listSignalRegistries, listRecordingDomains, validateRecordingDomainEvent (runtime-execution.ts): pure/static catalogs or validation; validateRecordingDomainEvent has an optional `projectId` but does no storage access, so left workspace.
- clientGatewaySnapshot, listClientGatewayItems, revokeClientTrust, startClientRecording, stopClientRecording, captureClientSnapshot, executeClientAction (client-gateway.ts): scoped by client session id / trusted client id, no owned-resource kind exists for them. startClientRecording has an optional `projectId` (null allowed), so the project is not reliably declared; left workspace. These are workspace-wide content that is not per-item filterable (gateway lists are the whole gateway).
- getFlowBootstrapGenerationReadiness (llm-generation.ts): handler refuses any request field, so there is no project to name.
- runtimeBuildIdentity (diagnostics/runtime-identity.ts): build identity, no scope.

## custom, list, creates
- caches.ts `listProjectUiCacheStats`: `custom(["project","*"], ...)`: `payload.projectId` is optional in the handler; non-empty string gives that project, otherwise workspace (stats across projects).
- conversations.ts `listConversations`: `custom(["project","*"], ...)`: project when `payload.projectId` is given (handler asserts it), else workspace (it searches every project from `listProjects`). Plus `list` over `payload.conversations`, each item's project from `item.projectId`, `replace` rebuilds `{...payload, conversations: kept}`. Note: the handler's across-projects branch already uses the domain entitlement of `listProjects`; the `list` filter adds the IAM per-project filter on top.
- projects.ts `projects`: `workspace()` + `list` over `payload.projects` (item ref `{kind:"project", projectId: item.id}`, replace sets `projects` only; `categories` untouched).
- projects.ts `createProject`: `workspace()` + `creates: payload.project.id`.

## Other choices worth checking
- startRuntimeSession, runRuntimeSession use `project()`: `payload.projectId` is optional (`string | null`) and a flow can be passed inline; a missing projectId becomes the registry's sentinel (no owner, so owner-conditioned grants fail). cancelRuntimeSession uses `projectChild("run","runId")`.
- getFlowSpend, getFlowAdaptation, reviewFlowAdaptation, all router.ts flow endpoints, all llm-generation.ts flow endpoints: `projectChild("flow","flowId")`. listFlowAdaptations and listFlowRuns use `project()` (flowId optional).
- datasets.ts: `listRunDatasets`, `deleteRunDatasets` use `projectChild("run","runId")` (datasetId optional on delete); `getRunDatasetPage`, `exportRunDataset`, `listDatasetRuns` use `projectChild("dataset","datasetId")`; `listProjectDatasets` uses `project()`.
- Conversation endpoints other than the list use `project()` (no conversation child kind exists).
- appendRecordingDomainEvent uses `projectChild("recording","recordingId")`; `projectId` there is optional in its type, same sentinel caveat.
- The `custom` resource types `["project","*"]` is my choice for a resource that is either a project or the workspace; the catalog's resourceTypes for these actions is the placeholder `["*"]`.
