## What changed and why

### Design

- **One gate, `ProgramIamGate`** (`programs/_shared/iam/program-iam-gate.ts`). It turns a `ProgramApiActor` into a compiled policy set, a principal `user/<userId>`, an `IamRequestContext` and an `IamRequestAuthorizer`. It builds the `IamRequestAuthorizer` directly rather than through `IamAuthorizer.forRequest`, so it can cache compiled sets and see `fullAccess` before deciding whether to look up owners. It fails closed the same way B2 does: an unreadable source, or a set that will not compile, becomes an empty policy set, so every decision is a recorded implicit deny.
- **`local` and `self-hosted`.**
  - Identity is the role's predefined policies (`rolePolicyNames`) **plus** `FluxIQPermissions`, an inline identity policy that allows exactly the actions whose registered permission the actor holds.
  - The session is always `FluxIQPermissionSession`, which allows the same set.
  - So the decision is identity AND session, which equals `permissions.includes` by construction, for every actor: an edited role, an unmapped role, a `user` role, a paired client.
  - An actor holding all eight permissions gets `Allow *` on the workspace content and the workspace FRN instead of a list. Both policies are then full-access grants, so an admin keeps the list fast path (tested: `compiled.fullAccess === true`, and a list costs 2 audit rows).
  - An `ops` action that several programs register is allowed per program FRN when the actor holds it for only some of them. Only `ops` actions can be shared, and the program FRN tells them apart, so each decision stays per registration.
  - Compiled sets are cached by (userId, roleId, sorted permissions, route override), capped at 256 entries and evicted first-in first-out. `register()` clears the cache.
- **`service`.** Policies come from `source.resolvePolicySet(principal)`, plus `FluxIQServiceGuardrail` (added unless already present). A paired client also gets the permission session; no one else does. With no source, everything is denied. Nothing is cached.
- **Resources** (`describe-resource.ts`, `id-segment.ts`, `owned-ref-id.ts`).
  - FRNs are built through `formatFluxIQResourceName` and `platform/iam/frn`.
  - An id that is not a plain FRN segment is encoded as `~` plus its UTF-8 bytes in hex, or as `~~` plus its SHA-256 when longer than 63 bytes. A plain id starting with `~` is encoded too, so the forms cannot collide.
  - A missing id (absent, not a string, or empty) becomes the sentinel `~` with no owner.
  - A project child is named under its project and carries the project's owner, but has no owner when either id is missing.
  - A `user` FRN is owned by that user.
  - An unknown ref kind gives a non-FRN string, which is denied for everyone.
  - Owners are encoded the same way as principal ids.
  - Owners are looked up only under `service`, and only when the full-access grant does not already cover every resource. Under `local`/`self-hosted` no decision can depend on an owner, so a viewer's list never touches storage for authorization.
  - A resolver that throws fails the call; its error is never read as "no owner".
  - An undeclared registration falls back to B2's rule: the program FRN for `ops`, otherwise the workspace FRN.
- **`call()` order:**
  1. not found
  2. no actor
  3. IAM decision, one audit row (deny gives `authorization.forbidden`)
  4. inside the measured scope: the PIN check for `destructive` (unchanged), the handler, then on success:
     - `creates` calls `recordOwner(rawId, actor.userId)`
     - `list` goes through `IamRequestAuthorizer.filter` with `itemAction ?? action`, scoped to the call's first resource; the payload comes back untouched when nothing was dropped.
- **Refusal shape.** `{ ok: false, error, errorCode: "authorization.forbidden" }`. The error is `Permission required: <permission>` whenever the actor lacks the permission, which is every deny under local and self-hosted (identical to today). It is `Not authorized: <action>` for a policy deny under `service`.
- **`authorize({ actor, action, permission, resources?, programId?, origin? })`** (for lane H2) returns `{ allowed: true, decision }` or `{ allowed: false, decision | null, response }`. For the route's action, the permission session uses the route's own `permission`, replacing any registration of the same action. Under local this is still exactly `permissions.includes(permission)`.
- **Origin.** `extension-chat` for `channel: "paired-client"`, otherwise `panel`; `authorize` can override it.
- **Request ids** are decimal (`<epoch ms><3-digit counter>`), because the audit store says non-decimal ids are costly.

## Open questions or contradictions found

1. **`workspace.ts` is missing its import** (above). The supervisor needs to fix it, or send the owning worker back.
2. **The `browser` vocabulary fails the `web-vocabulary` rule.** It comes from the seam and the frozen FRN contract (`gateway` type `browser`). It needs either a baseline entry (`pnpm structure:baseline`, recorded as a deliberate exception) or a seam rename. That is the supervisor's decision; I did not work around the rule.
3. **No fast path anywhere under `service`.** `FluxIQServiceGuardrail` holds `Deny` statements, which disables `fullAccess` for every set, including `FluxIQOwnerFullAccess`. So every hosted list is decided item by item, with owner lookups and one audit row per item. That is correct, but it contradicts the plan's "single-owner list endpoints skip per-item checks" for hosted personal workspaces. It is a B2 evaluator rule (`denies.length === 0`), so I did not change it.
4. **A paired client under `service` gets only the permission session, as briefed, not `FluxIQBrowserSession`.** The plan says a connected browser is narrowed by `FluxIQBrowserSession`. Adding it would deny destructive actions beyond today's behaviour, so it needs a lead decision.
5. **`FluxIQUserAccess` changed but kept `v1`.** No decision has ever cited it, since enforcement starts here, and `predefined-policies.test.ts` pins every policy at `v1`. If audit citations of `v1` must mean one document, bump it and that test together.
6. **Docs.** `docs/architecture/platform.md` (Status, The resource rule, Parity, Known gaps: "FluxIQUserAccess grants little until B3") is now stale. It is not in my paths.
7. **Undeclared registrations.** The registry still accepts them (the type allows them, for test doubles). The plan says public profiles should refuse an endpoint without an action and resource at startup. The completeness test enforces this for the live registry, but a startup refusal under `service` is not built.
