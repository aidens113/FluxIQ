# t808 C0: eviction prerequisites for per-workspace instances

Tree `fxwork/t808/!FluxIQ`, branch task/t808-hosted-tenancy-c0. Nothing committed.

## Outcome

`FluxIQ.close()` now leaves nothing behind in the process. It detaches the instance's
activity-hub subscription, closes only its own storage root's SQLite pool, and takes a mode:
`shutdown` (the default, today's behaviour) or `evict`. A `HeldKeys` can be injected through
`FluxIQOptions.heldKeys`. `evict` leaves an injected custody held for the next instance; an
instance's own custody is always revoked and zeroed. The leak test proves that a closed,
dropped instance is garbage-collected and leaves no hub subscriber, pool, timer or key.

A single local install is unchanged. It injects no `HeldKeys`, closes in `shutdown` mode, and
has one storage root, so close revokes every unlock and closes the same connections as before.

## Design decisions (supervisor)

- **Hub: a disposable subscription, not a per-instance hub.** A per-instance hub needs the emit
  path to find its hub, and its readers are `programs/automation-studio/api/handlers/activity.ts`
  (`programs/*/api/**`, which B3 owns) and `runtime/service/project-build/run.ts` (the framework
  lanes' area). Both were forbidden. The hub is still shared by every instance in a process, so
  workspace A's events still reach B's gateway, filtered only by project id. That fan-out is C3's
  per-workspace singleton work (S4 D2). C0 removes only the retention and the delivery to a
  closed instance.
- **Connections: one pool per storage root.** Storage resolves its repository from a file path
  (`sqliteStateForPath`), with no instance in reach. Keying by the resolved storage root
  (`programStateRoot(dir).dir`) gives each workspace root its own pool without threading an
  instance through storage. `FluxIQ.close()` closes `paths.fluxiq`'s root. Two instances on one
  root share one pool, which is the right behaviour for a reload.
- **HeldKeys: injectable, with an eviction mode.** This follows H0-S5's first option.
  `SecretKeysService.close({ mode: "evict" })` skips `revokeAll` only for an injected
  `HeldKeys`. The workspace manager (C1) owns the final `heldKeys.revokeAll()` on deletion or
  shutdown. Plan line 583 says an eviction locks keys; with injected custody it no longer does.
  The lead may want to reword that line.
- **Extensibility for C3's `iam`.** `createGlobalProgramRuntime(paths, options)` takes a named,
  exported `GlobalProgramRuntimeOptions`. C3 adds `iam?:` beside `heldKeys`.

## Not verified

- **Standalone Core tsc.** Its waiter never got the shared lock, which other lanes held for over
  30 minutes. I stopped it before it ran, and `pnpm check`'s fresh `fluxiq:check` (the same
  `tsc --noEmit`) passed in its place.
- **Gateway-trace and offline-trial `installed` slots** (S4 rows 4 and 5). They are set only when
  tracing is on (the Lab). The last instance stays reachable through them, so the leak test runs
  with tracing off. They are C3's.
- **Eviction while busy.** In-flight work of an evicted instance is not cancelled; it fails
  closed. A pool closed under a running `keepWhile` is recreated for later operations, unkept.
  The manager must pin busy workspaces, as the plan says.
- **Unusual storage layouts.** A storage directory configured outside the `.fluxiq` root (custom
  `FLUXIQ_RECORDINGS_DIR`) resolves to a different pool root, which `FluxIQ.close()` does not
  close. Legacy v1 storage keeps no connections, so it is unaffected.
- No live or browser run (none needed). No full suites, per the twice-a-day rule.
