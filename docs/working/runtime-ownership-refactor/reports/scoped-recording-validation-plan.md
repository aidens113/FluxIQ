## Verified owners and scope availability

- `RecordingIngressPolicy` has three EXISTING one-argument methods: entry(value), commandTarget(value), initialState(value). Generic capture invokes them in `capture/store.ts`, `capture/action.ts` and `lifecycle/client/open.ts`. No callback currently receives an authenticated domain.
- Studio bridge installs one global `studioRecordingIngress`. Its initial-state/evidence checks are strict Core rules; only its outer target guard plus inner element is/validate and command target encoding belong downstream. The generic decoder already accepts a target guard and preserves the complete append/result/evidence union.
- `capture/store.ts` captures the actual active address before decoding, but decodes BEFORE its inactive-message discard. `capture/action.ts` captures active before awaiting flush, then calls commandTarget and appends to that original address. Keep these address/order semantics; never reselect another active recording after await.
- Host start currently takes domain from input/domain metadata; client start prefers input.domainId/input.metadata before session metadata. An explicit input.environment is persisted independently, so active.domainId can differ from returned recording.environment.domainId. `RecordingStartContext` currently approves only projectId/taskId; Service.createRecording currently persists the supplied domain without asserting the project domain.
- There IS an existing authenticated domain authority: pairing-flow stores declaredDomainId into the ORIGINAL trusted-client record approved by the operator; lifecycle resume requires that same bound domain (legacy undefined is rejected). `gateway.snapshot().trustedClients` exposes that domain/status without token hash. Session metadata originated in hello and is routing data; select from the active trust record, not arbitrary current metadata.
- Existing `RecordingStartPolicy.context` is the right approved-address seam. Studio's context provider retains its original bridge receiver/request; after it chooses project, `service.assertProjectDomainAccess(projectId, approvedDomain)` already checks the actual persisted project scope. API create already overrides payload domain with authenticated request.scope.domainId.
- Append storage has the decisive original state: `service.ts:appendRecordingEvents` holds the existing recording mutation lock, reads raw recording, checks finalized state, then selects target preparation from recording.environment.domainId. Add raw target validation THERE before normalization/dehydration/writes. The HTTP append handler currently delegates directly, so ingress-only validation would leave a real bypass.
- Existing active/closed/pending maps and write-order batching are the sole recording/address authorities. No new global/domain/current-context/WeakMap registry is needed. `updateRecording` does not expose an environment/domain mutation, but stored corruption, legacy missing domains and restart still require explicit checks.
- Standalone Core `model/validation/recording.ts` is a public adapter with browser defaults; source search found no production caller beyond its declaration/export. Its actual consumers are model/compatibility tests. A supplied RecordingSession object alone is NOT a trusted domain selector.
