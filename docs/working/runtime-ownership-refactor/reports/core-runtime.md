# Core Automation Studio ownership audit

## Inventory and scope

- `rg --files packages/fluxiq/src/programs/automation-studio` returned 4,544 paths: 2,671 production source files and 1,873 test/support files. The source/test split counts paths under `tests/` or ending `.test.ts` as tests.
- Production source by top-level area: `runtime/` 2,238; `storage/` 175; `nodes/` 94; `model/` 72; `api/` 63; `testing/` 6; `dsl/` 5; `normalization/` 3; `client-gateway/` 3; `fingerprinting/` 3; `learning/` 2; `mining/` 2; `ui/` 2, plus root exports/metadata/types.
- Largest clusters include `runtime/flow-bootstrap` (395 files), `runtime/service` (376), `runtime/llm` (374), `runtime/result-verification` (274), `runtime/executor` (211), and `storage/project` (149). Counts include directories beneath each cluster.

## Ownership assessment

The large runtime is substantially Automation Studio's authoring and execution orchestration, not a misplaced generic runtime. `runtime/executor/graph-run.ts` consumes `AutomationStudioFlowDocument`, Automation Studio nodes, state routing, trace withholding, person-needed outcomes, activity, and runtime-repeat policies. `runtime/composite-executor.ts` runs Studio flow artifacts and published snapshots. Bootstrap, recovery, result verification, durable project state, action permissions, model-provider orchestration, and trace handling carry the same Studio-specific contracts and lifecycle. These are cohesive Studio concerns despite their size.

The generic framework equivalents already exist at `packages/fluxiq/src/flows/index.ts` and `packages/fluxiq/src/engine/index.ts`. The latter uses generic `FlowDocument`, `ComponentRegistry`, `IoRegistry`, and `FrameworkResult`; it does not import Automation Studio. The Automation Studio executor imports Studio model/node contracts and does not import the generic engine or flows. This is a parallel, richer program runtime rather than a misplaced implementation of the existing generic engine. Moving the graph executor into `engine/` would couple that layer to Studio contracts and invert ownership; replacing it with the generic engine would lose Studio's retry, route, permission, trace, and durable-run semantics.

The main barrel `programs/automation-studio/index.ts` exports the program's API, runtime, model, storage, DSL, nodes, testing support, and UI. `packages/fluxiq/package.json` also exposes targeted public paths including `fluxiq/automation-studio`, `/nodes`, `/action-effect`, `/actionability`, `/dsl`, `/fingerprinting`, and runtime-specific model/permission paths. Downstream's `domain/src/runtime/tests/state-routing-run.test.ts` directly imports `runAutomationStudioGraph`, `AutomationStudioFlowDocument`, node/options/trace types from `fluxiq/automation-studio`; it supplies a web host and effect dispatcher to test the real Core executor. `domain/src` and `apps/extension/src` together have 70 files importing `fluxiq/automation-studio/nodes`. Preserve current names as compatibility exports while migrating internal consumers.

## Migration groups and first implementation

The importing web domain is an actual consumer of the public Automation Studio runtime contract. This is therefore a framework capability boundary, not a claim that another global program already reuses every executor feature. The safe direction is to move reusable execution kernel/contracts into framework-owned runtime areas while keeping authoring, persistence, LLM build policy, traces, and Studio-specific orchestration under `programs/automation-studio`. Do not move the whole runtime directory as one unit: its dependency closure is much larger than the executor and includes Studio-specific behavior.

## Cycles, compatibility and checks

- Directly inspected dependency direction is one-way: generic `engine` imports `flows`, `components`, `core`, and `io`; Automation Studio executor imports its program's model, nodes, and runtime collaborators. The generic engine/flows layers did not import Studio modules in the scanned results, so there is no current cycle to resolve by moving both trees together. The `_shared/runtime.ts` program composition root imports and assembles Studio and other program services, which is a composition consumer, not a reason to move those services into `_shared`. A complete cycle proof was not run; use the existing structure audit/import-cycle rule before and after extraction.
- Internal runtime callers depend heavily on executor trace/options types (composite execution, recovery/adaptation, live patch and service). Move these types and the executor as a coordinated interface change. The dominant risk is semantic, not just path churn: the core must preserve Studio trace withholding, retry/reacquisition and lasting-act safety via host policy ports.
- Compatibility risk is high because `programs/automation-studio/index.ts`, `runtime/index.ts`, and package exports point into this tree. Keep every current public path as a façade/re-export during migration; first inventory all `packages/fluxiq/package.json` subpaths and downstream consumers, then remove shims only in a separately approved breaking release.
- Exact focused checks after migration: from Core root, `pnpm --filter fluxiq check`; focused Core tests via `pnpm --filter fluxiq exec vitest run src/programs/automation-studio/runtime/executor src/engine/flow-execution src/engine/tests/index.test.ts`; downstream regression `pnpm --filter @fluxiq-web-extension/domain exec vitest run src/runtime/tests/state-routing-run.test.ts`; then Core `pnpm exec node scripts/build-cache/cli.mjs structure-audit:check` (check root command/config before dispatch). Keep the extension package typecheck in the acceptance set if public exports change. No checks run in this read-only discovery.
