## Findings

**P1 — delayed finalization confuses the same recording ID in different projects.** `client-gateway/recording/lifecycle/stop.ts:16` and `lifecycle/client/stop.ts:19` delete the current active ref by recordingId alone after awaiting finalization. Stop P/`same-id`, hold its actual finalize, then approve/start Q/`same-id`; finishing P deletes Q's active slot. Q's later capture is discarded, while the remembered closed address can point back at P. Existing lifecycle race oracles use different old/new IDs, so do not cover this actual namespace case.
The same cause exists in `writes/outcome.ts:15`: a failed P append confirmed finalized at P chooses a current Q active ref solely because its ID matches, attributing P's closure to Q. `lifecycle/remember.ts:7` also retains an old closed project when a different project closes the same ID. These are one address-comparison defect family; do not change address selection from untrusted wire projectId.
Narrow proof required: host/client Stop with real P/Q same-ID recordings and held original finalize; Q must remain active/writable/unfinalized after P settles. Also hold a P append, finalize P, make Q/same-ID active and reject P's append; discard/closed diagnostics must retain P, never claim Q is finalized. Compare complete captured project/recording addresses or original ref identity before clearing/adopting state; no new registry.

**P1 — semantic raw-entry rejection occurs after preparation can perform IO.** `programs/automation-studio/runtime/service.ts:795–800` decodes the full batch first but only checks canonical session issues AFTER `prepareRecordingEntriesForStorage`. The decoder's `client-gateway/recording/decoding/entry.ts:11` accepts every finite confidence, while `runtime/recording/validation/recording.ts:60` rejects values outside [0,1]. Thus confidence2 reaches an action target normalizer before refusal. A confidence2 `client.state_snapshot` observation with valid payload.state also reaches `object-documents.ts:148,170` objectStore.putBytes when that project store is enabled, before the rejected batch completes.
The new direct-batch test catches domain parameter/target errors earlier, but does not prove zero side effects for shared semantic errors. Narrow proof: actual Service action/snapshot confidence2, including a mixed batch, must reject `recording.invalid_entry` with zero target normalization/object puts/mirror/stream/index changes and unchanged timeline. Apply the actual shared semantic checks before preparation; preserve omitted ID/time/retry identity rather than generate defaults twice. Keep final prepared-session validation too.

**P2 — direct create bypasses the existing strict initial-state guard.** `programs/automation-studio/api/handlers/recordings.ts:129–130` casts raw payload and delegates to create. Service `createRecording` constructs the session and checks policy availability at `service.ts:757–758`, then mutates mirror at 762 without invoking `studioRecordingIngress.initialState` (`client-gateway/ingress/policy.ts:11`) or equivalent strict state validation. For example initialState:{} reaches a mutation route that client open correctly refuses as `recording.invalid_initial_state`. A TypeScript request alias is not runtime decoding.
Narrow proof: malformed initial state through actual authenticated API/Service create must refuse before mirror/project-file/index writes, retaining no partial recording. Validate through the existing strict Core state owner before first mutation; do not add browser interpretation or a replacement state DTO. This is source evidence only; durable end-state/error behavior was not executed.
