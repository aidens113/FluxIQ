# Framework persistence migration plan

Status: read-only discovery complete; no implementation or new acceptance claim. Source/test freeze preserved. Brief: [framework persistence discovery](../briefs/framework-persistence-migration-discovery.md). The user requires Automation Studio to contain only panel UI, view state and thin framework control adapters. Its current persistence, queues, validation and backend assembly are temporary locations.

Recommendation: execute cut 1 first, independently of C's observation migration and B's run-context repair. Cut 2 moves the real project record owner after its named rich contract dependencies are canonical; cut 3 moves the real queued writers after C's ledger dependencies are canonical. Aliases preserve compatibility; they do not count as moving an implementation while its body remains in Studio.

All source paths below are relative to `packages/fluxiq/src/`. Proposed destinations are concrete ownership boundaries for a subsequent release, not files created by this report. Root retains parent/package exports, common service integration, configuration, baselines and shared working documents. Each new directory needs a barrel; new leaves have one exported authority and obey existing budgets without transferring or raising baseline entries.

## Observed ownership and invariants

- `programs/automation-studio/runtime/project-agents/record/store.ts` constructs its own Documents. There is no injected-document implementation port. It owns create/read/summary, task/plan/brief/return/receipt/allowance/act/toggle/decision/end writes, cross-record validation and first refusal. Moving only its selected receipt methods would leave the persistence authority behind.
- `record/documents.ts` owns rootless JSON round-trip memory and per-document serialization. Its persistent implementation constructs the actual `ProgramJsonStore`; only the pinned original storage method acknowledges an owning commit. Supplied change/clock/records/persist callbacks are observed before invocation. Replaced storage methods are unsupported without authentic completion.
- The reusable storage implementation is currently `programs/_shared/storage.ts`, backed by `_shared/state-root.ts`, `_shared/state-connections.ts` and `database-manager/storage/{sqlite-repository,connection-pool,operation-queue}.ts`. These are Core storage authorities housed under programs, not panel adapters. `database-manager` service/panel operations and administrative Migration DTOs are different owners and are outside cut 1.
- Store `now?: () => number` is the actual clock seam. Preserve its original receiver and default pinned `Date.now`; an injected clock gets no purity or receipt merely by returning. The record/document/queue owners need no model, provider or presentation callback. Their rich summaries and refusal code/path are data; historical Error names/messages remain compatible.
- Acts/toggles retain exact original records functions and receivers at bind. ProjectLedger captures the original options sink/recorded object before queueing and pins its lexical persist callback. Their serialized queues, deduplication, first-error retention, legacy void enqueue and explicit original-Promise flush APIs are authorities to move, not UI conveniences.

Storage bytes and identity must remain unchanged: root resolution/config stamps, `safeSegment`, database file/table/scope mapping, pool lifetime and original class/singleton identities; no data migration or copied second store is needed. Layout 1 domain databases remain `domains/<id>.sqlite`, layout 2 `domains/<id>/domain.sqlite`, and the unscoped database remains `global.sqlite`. State routing still strips `programs/` into `program.state` or `artifacts/automation-studio/` into `automation.state`; the existing write envelope's `kind: "program.state"` is also preserved, even on the latter route.

The build document path stays `<project>/flows/<flow>/project-builds/<build>/build.json` and `returns/<brief>.json`, relative to the existing actual project root. Its memory key stays `JSON.stringify([projectId, flowId, buildId, name])`. File writes retain `{ version: 1, data }`, two-space JSON plus final newline, temporary-write/rename acknowledgement and lock release. SQL writes retain actual put acknowledgement and transaction behavior. Receipt issuance remains after those acknowledgements; no arbitrary injected Promise becomes an IO witness.
