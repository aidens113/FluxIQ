## What changed and why

### A17: createDefaultFlow retired

### A16: storage_required stays
- Through `runRuntimeSession`, neither case of `command_execution.storage_required` can be reached:
  - **A run with no project:** the instruction gate (`instructionAuthority.assert`) refuses it first.
  - **A service with no storage:** `storageAvailable` is false only when the service has neither `dataDir` nor `storageRootDir`. On such a service `createFlow` throws ("no storage root ... names no file for it"), and the gate's `getFlow` throws the same error before the rule. A probe confirmed both.
- Why it stays:
  - `AutomationStudioRequiredCommandRun` owns the required-mode rule, which is that durable command outcomes need a project and storage.
  - The gate is a different concern (instructions), and refusing here first is only a matter of call order in `service.ts`. If the rule were removed, the guarantee would depend silently on that order.
  - The class is used only by `service.ts`, so keeping the check costs nothing.
- `service/command-execution/lifecycle.ts`: a three-line comment says why the rule stays. The code is unchanged.
- New test `service/command-execution/tests/storage-required-reach.test.ts`: on a service with no storage, `createFlow` is refused, and a required run is refused before the rule, both with and without a project. The class still throws `storage_required` for both cases on its own.

### A18: scope kinds answer the same on both paths
- **How SQL stores them:** project SQL stores `adaptation_review` as `flow` and `on_error` as `error`, and reads `error` back as `on_error`. SQL cannot tell a review scope that names no Subflow from a Flow scope. The summary index keeps each instruction's own kind.
- **What diverged before:**
  - An unfiltered page reported a review instruction as `flow` from SQL but as `adaptation_review` from the index.
  - The filters `scopeKind: adaptation_review`, `flow` and `error` matched different rows on the two paths.
  - A Subflow filter took in its Flow's review instructions on SQL but not on the index.
  - Sorting by scope ordered `error` and `on_error` differently.
- **The fix:** a new module `service/summaries/instruction-scope-kind.ts` (`automationStudioInstructionListingScopeKind`, exported from the summaries barrel). It gives:
  - `key`: the kind as SQL stores it.
  - `reported`: the kind as SQL reads it back.
  - `sqlKey`: a `case` expression that does the same over the JSON summary table.
- `service/summaries/store.ts` `listFlowInstructionSummariesUnheld`: the in-memory index branch and the JSON-summary-table SQL branch now filter, scope (Flow and Subflow clauses) and sort by `key`, and report `reported`. The typed SQL branch takes the same normalised filter. Nothing stored changes.
- **The resulting vocabulary:**
  - Review scopes are listed as `flow`, which is what the SQL path, the usual path for a stored service, already returned.
  - `error` and `on_error` name the same scopes.
  - A filter of `adaptation_review` behaves as `flow` on both paths.
- `service/summaries/tests/instruction-scope-parity.test.ts`: the seed can add five instructions of the two kinds (review with no Subflow, with Subflow a, with Subflow b; error, and error on Subflow a). A new test compares id and reported kind for the old filters plus eight new ones, then checks four more things:
  - order by scope;
  - the reported kinds;
  - that `error` and `on_error` give the same result;
  - that the earlier test's exact results are unchanged.

  The new test failed against the old `store.ts` (checked by restoring HEAD's copy) and passes with the change.

### A15: the missing-instructions refusal carries the Flow Bootstrap diagnostic again
Callers that classify build failures by that diagnostic, as found by grepping both repositories:
- **Core `api/handlers/llm-generation.ts:140-150`:**
  - It parses the thrown error with `parseAutomationStudioFlowBootstrapGenerationError`.
  - An `AutomationInstructionError` is not a Flow Bootstrap error, so the build API was answering `"Flow Bootstrap generation failed (flow_bootstrap.unclassified_failure)."` with no diagnostic, and recording nothing in `failedBuilds`.
  - That made it the clearest regression of the three.
- **Core `conversations/commands/progress.ts:192`:** the chat's `CODE_WORDS` maps `active_instructions_required$` to "the Flow has no instruction saying what it should do", and `STAGE_WORDS` reads the diagnostic stage.
- **Downstream Lab** (`packages/test-runner/src/flow-lane/creation/build-proposal.ts:623-661`, `demo-llm-create-ui/generation-failure.ts:55-90`):
  - Both read refusals through Core's `parseAutomationStudioFlowBootstrapFailureDiagnostic`, which needs a stage, a provider invocation and accounting.
  - Without them a refusal became `lab.generation_http_<status>` or `generation.http-400`, with the provider calls unknown.
  - Its tests (`failure-sanitizer.test.ts:235-239`, `browser-evidence.test.ts:27`) still expect `flow_bootstrap.active_instructions_required`.
- **Not a build caller:** the extension's `automation.instructions_required` handling (`core-api.ts:171`, `panel/state/request.ts:32`, `hold-control.ts:75`) covers runs and resume. The extension does not call the build endpoint.

The fix:
- `runtime/service.ts:1520`, one line changed in place: the build now asks `instructionAuthority.readiness` and, when not ready, throws `flowBootstrapPhaseFailure("pre_provider_validation", undefined, "flow_bootstrap.active_instructions_required")`.
  - This is the same check as `assert` (projectId and flowId are always present at that point), and it is still made before any provider call or resolver.
  - The build's existing catch turns it into the full diagnostic (stage, `providerInvocation: "not_attempted"`, `providerResponse: "not_received"`, accounting), exactly as before t519.
  - Other `AutomationInstructionError`s inside the build, such as supporting recordings, still pass through unchanged.
- `runtime/tests/service-bootstrap/tests/accounting.test.ts` and `rejections.test.ts`: restored to the expectations t546 had replaced. They expect the full diagnostic object and the error message `Flow Bootstrap generation failed (flow_bootstrap.active_instructions_required).`

## Open questions or contradictions found

1. **A separate, older SQL/index divergence (not fixed, outside A18's mapping):**
   - `writeSqlFlowInstruction` is called with `.catch(() => undefined)` (`service.ts:3249`).
   - An instruction whose scope names a node (`node`, or `on_error` with `nodeId`) that is not in `graph_nodes` fails that SQL write, so it is silently missing from SQL while the index has it.
   - Once SQL holds any row for a project, the typed SQL page omits such instructions.
   - The parity test therefore leaves `nodeId` out of its `on_error` fixtures.
   - Worth its own follow-up.
2. **A18's chosen vocabulary loses a distinction:** both paths list review scopes as `flow`, so a listing cannot pick out review instructions by kind on either path. Keeping the distinction would mean storing the kind in SQL (a schema or data change, which the brief ruled out).
3. **A15:** the build's refusal code is `flow_bootstrap.active_instructions_required` again, not `automation.instructions_required`. No build caller in either repository reads the latter, but anything added since t519 that expects it from a build would now miss.
