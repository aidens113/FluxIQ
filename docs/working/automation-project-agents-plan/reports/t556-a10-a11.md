### A10: answers go to the right ask (`conversations/commands/answer-ask.ts`)

- `askMeant` now returns `{ ask } | { refused } | null`:
  - If the answer names an ask this thread has, that ask is used, whatever else is pending. This is unchanged.
  - Otherwise, if **more than one** ask is pending in the thread, the answer is refused and nothing is settled. This covers an answer that names no ask and one that names an ask the thread does not have.
  - Otherwise the single pending ask is used. With no pending ask the result is null. Both are today's behaviour.
- **Revised after the supervisor's follow-up: no ask ids in the thread (t276).** The refusal names each waiting ask by its own question words, which are its turn's text as the person saw it. It adds the kind of answer each one takes (yes-or-no, a choice between the option labels, or the person's own words), plus "about <control name>" when the ask has one, and ends by telling the person to answer the one they mean on the question itself. The panel's buttons on each question already answer by id. Example: `2 questions are waiting here, so I could not tell which one this answers: "Shall I keep the notes I made?", a yes-or-no question about Save the list; "Which of these should I open?", a choice between "The first", "The second". Answer the one you mean on the question itself. Nothing was changed.` An answer naming an unknown id now opens "That question is not in this conversation, and 2 questions...", which echoes no id.
- **The turn reader.** I added an optional `getTurn?({ projectId, conversationId, turnId })` to `AutomationStudioConversationCommandHost` in `conversations/commands/command.ts`. The real host, `AutomationStudioConversations`, already implements exactly that signature (`conversations.ts:311`), so no implementation change was needed. A host without it names each ask by the kind of answer it takes alone, still with no id.
- **No ids in a structured record.** No client needs them. The extension's buttons carry each ask's id on its own turn, and `AutomationStudioConversationCommandOutcome` has no field a client reads for this, so I added none.
- The list goes through `progress.failed(cause, { ending })`, so it is the failure's own account and is not passed through the plain-cause filter, which could otherwise clear a question whose words read like a code. `error` carries a plain cause: "more than one question is waiting in this conversation and the answer did not say which".
- The `askId` argument's description, which the chat model sees, now reads "Left out, it is the one question still waiting in this conversation; when more than one is waiting it must be named." The header comment records the A10 rule.

### A11: the start hook gets the holder's lease (`service/candidate-trial/contracts.ts`, `service/candidate-trial/run.ts`)

- `AutomationStudioPrepareCandidateStart` input gains an optional `lease?: AutomationStudioHostResourceLease`. The JSDoc on the type states the domain contract: under a lease, the hook resets only the resource `lease.resourceKey` names (on `lease.sessionId` when set) and nothing another holder may be using. Without a lease it resets as before.
- `automationStudioCandidateTrialStart` reads the lease from `AutomationStudioHostLeaseScope.current()`. This is the same async-context scope the dispatcher runs each brief in, and `service/project-build/subflow-trials.ts` already reads it the same way for session admission. The function then:
  - with no lease scope, calls the hook with exactly the old input. The test checks that the `lease` key is absent.
  - with a current lease, passes a `structuredClone` of it, so a hook cannot change the holder's lease object.
  - with a lease that is no longer current (released or reissued, i.e. work that outlived its lease), never calls the hook. It returns `{ status: "failed", code: "candidate.trial_start_lease_stale", failure: "the host resource lease this trial ran under is no longer held" }`, and the trial then ends on it without running. The brief did not ask for this check. I added it because a stale holder's reset is exactly the "acts outside the holder's resource" case. The supervisor may want to keep it or drop it.
- This function serves the trial port's `prepareStart` (trial gate, before the reset check), whole-candidate trials and subflow partial trials (`service/subflow-trial/run.ts`), so all three uses get the lease with no change to those files. Importing goes straight to `project-agents/host-resources/index.ts`, not the `project-agents` barrel, because `project-agents/dispatch/types.ts` imports `service/candidate-trial` and the barrel would close a cycle. `host-resources` imports nothing back.

## Open questions or contradictions found

Since the follow-up, the refusal no longer shows them either. A typed answer therefore cannot name an ask, and the refusal sends the person to the question itself. The panel buttons are unaffected: the extension already sends `answer-ask` with an explicit `askId` (`apps/extension/src/background/panel/conversation-relay.ts:109-112`, `panel/chat/conversation/controller.ts:394-404`). **No extension change is required for A10.** The extension's chat sends only the capability id, and Core's model fills the arguments. If typed answers should route when several asks are waiting, the change belongs in Core, outside this brief: give the decision model each pending ask's id beside its question turn, in a channel that is not thread text. That would be the model request built in `conversations/instructions/request.ts` or `prompt.ts`, or the transcript built in `conversations.ts`.
2. Ask ids in thread text: resolved by the supervisor's follow-up (see A10 above).
