# P10 CC11: trusted resolved control intent

Outcome: Done (read-only design). Inspected the primary Core/Down source; t832's unrelated guidance metadata is outside this design. Only this report was written. No runtime or compatibility verification is claimed.

In paths below, `C/` means Core `packages/fluxiq/src/programs/automation-studio/`; `D/` means this repository's `domain/src/`.

## Recommendation

Add one optional companion to the trusted public node-resolution answer, retain it in a Core-owned per-node sidecar, and use that sidecar in the existing candidate way-out check. Do not put intent in node parameters, model JSON, saved fingerprints, handler facts or a free-form client prompt. Move the English authoring classifier to Down. Keep the permission/effect gates and automatic interference clearing unchanged.

Four bare tags are insufficient if `accept` retains its truthful existing meaning. The current CC7 contract calls a consent acceptance `accept`, and automatic clearing must never press it. Authoring currently permits a pure consent response. Reclassifying that response as `dismiss` would conflate those different policies. Recommend this minimal additional generic annotation:

```ts
type AutomationStudioResolvedControlIntent =
  | Readonly<{
      intent: "accept";
      responseOnly?: true;
    }>
  | Readonly<{
      intent: "dismiss" | "neutral" | "navigate";
    }>;

// Companion on the existing trusted answer; never inside parameters:
{ status: "resolved", parameters, controlIntent?: AutomationStudioResolvedControlIntent }
```

`responseOnly:true` means the client identified this particular observed control as only answering the interruption containing it, not taking an underlying offer or doing an additional requested act. Consent acceptance remains `intent:"accept"`; the extra bit distinguishes its authoring role. The bit is not permission, a consequence declaration, an effect class, repeat safety, readiness or a command to press anything. It must not be consumed by CC7's automatic selection.

**Recommended frozen optional shape:** only omission of `controlIntent` means absent. A supplied companion is a plain own-data record (ordinary or null prototype), with exactly one required `intent` from those four exact strings and no symbols, accessors or unknown keys. Only `intent:"accept"` may carry an own `responseOnly`, and its only valid supplied value is literal `true`; false, explicit undefined, a different value, or that field on another intent is malformed. Supplied `controlIntent:undefined` is malformed too. No coercion, trimming, inherited values or getter execution. Clone/freeze the accepted record before keeping it. Malformed supplied metadata refuses the node through the existing invalid-resolution outcome; it never silently falls back to omission.

The generic Core predicate, under the current optional/handler and explicitly empty-consequences conditions, becomes `intent === "accept" && responseOnly !== true`. Missing intent triggers no Core English fallback and grants no authority: it only leaves this additional semantic diagnostic inapplicable. Normal resolution, explicit declarations, canonical effect floors, permission asks, scope restrictions and commit retry handling still apply. In particular, a generic web click's trusted floor is `commit`, not proof of a money/publication class (`D/actions/action-effect/table.ts:16-31`); do not claim that the floor independently detects an undeclared purchase. Complete, correctly bound web classification and the declaration gate remain necessary.

## What the current source actually does

- `C/runtime/flow-bootstrap/script-statements/way-out-steps.ts:69-85,109-139` reads English accepting/closing/consent regexes from resolved `parameters.element` words. It judges optional steps and handler bodies declaring `[]`, and leaves an explicitly lasting declaration to the permission gate. `candidate/submission.ts:255` is the only production caller found; the shared candidate controller also serves subflow submissions. The current checker is not a general saved-Flow or repair execution guard.
- **The current handler consent exception is model-forgeable at authoring time.** `way-out-steps.ts:103-106` trusts a nonnegated script fact matching `^dialog\s+consent\b`; `wordsAccept` then permits any non-offer-word acceptance. No relation to the resolved target's actual layer is checked. Core's literal dialog target bypass (`llm/harness-options/plan-fact-targets.ts:68-73`) is not positive evidence that this control belongs to a consent layer. A runtime fact can still prevent the handler running; this is a bypass of the authoring diagnostic, not proof of a dispatched lasting act.
- Core also permits standalone labels such as `Accept all` without positive observed consent context (`way-out-steps.ts:81-83,138`; owning tests at 53-57). Remove that label-only authority when moving the exception: an actual observed consent relationship must supply the response-only annotation.
- **Automatic clearing already enforces its stricter policy.** Extension `interference/way-out.ts:78-96,145-155` chooses a close/decline, consent decline, session continuation or rate-limit acknowledgement; `clear.ts:63-64` explicitly never auto-accepts consent. `obstruction/ways-out.ts:35,56-62` orders dismiss, neutral, accept, and Core `C/runtime/executor/node-execution/obstruction.ts:15-16` never auto-presses accept. Preserve these meanings and this behavior.
- **Authoring reject/necessary-only preference is advice, not an availability veto.** The system instruction says decline optional cookies unless instructed otherwise (`D/runtime/llm-evidence/system-instructions/instructions.ts:75`); current Core act/state guidance prefers reject/necessary and allows fallback accept. The current way-out checker does not prove that reject was absent before permitting acceptance. Preserve that preference and the no-reject positive path without claiming an enforcement that does not exist. Do not add a new preferred-control selection gate in this migration.

## Scripts, saved targets and repairs

- A model script or JSON plan cannot forge the companion by writing an extra key: Core's map is built only from the bound resolver return. Model-written targets remain handle-only, and conflicting literal identities still fail the existing `resolve-plan-node.ts:627-637` checks. A model-written consent fact no longer affects the exemption.
- Persist the same executable parameters/fingerprint as today. Intent is contextual (the control and containing interruption at that look), not durable element identity; putting it in `D/actions/types.ts` or Core fingerprint normalization would make stale/forged saved values appear authoritative. No fingerprint schema migration belongs here.
- An untouched inherited saved step is not newly approved by an absent sidecar; it continues under the existing inheritance and runtime permission/effect rules. A newly authored or amended control must obtain fresh trusted resolution. No view means no host consent exception, not an invented safety proof from the saved label.
- **Absolute host targets need an explicit receiving path.** Today `resolve-plan-node.ts:617` answers unchanged when no handle was replaced, before the handle-derived identity/intent path. Preserve the existing model restriction in `written-literals.ts:10-35`: new model scripts, JSON plans and repair steps still cannot supply absolute selector/element identities. For a recorded, hand-authored or host-held draft target, add a private target-store lookup which can return only the already captured intent of one exact retained control matching the host target's selector, frame/shadow scope, location/document and compatible observed identity. Perform that lookup before this unchanged return; unwrap Run Output first, as the current acting-step path does. Return a resolved answer with the same parameters plus the companion only on that positive unique host match; do not fabricate a handle view or infer intent from saved words. Conflicting retained matches use the existing ambiguous-target refusal. No matching retained evidence keeps the old unchanged/absent behavior and existing permission checks; it supplies no response-only exception and is not called safe. No browser query or extra capture is introduced. The helper is product-internal, not a new public test API.
- Repairs share `C/runtime/recovery/annotation/step-evidence-resolution.ts:145-185`, the packet-routing resolver and permission checks. Keep those checks and packet ownership intact and ignore saved/model intent fields there. The present way-out diagnostic only consumes candidate scripts; this unit must not claim to introduce a new CC11 guard over all repair patches or old saved Flows. Any such new policy needs a separate bounded design. Optional semantic classification must never lower a repair's resolved effect or declarations.

Compatible unknown behavior is explicit: an old/non-web resolver that omits the companion, a truly unclassified control, an inherited step skipped by existing resolution, or a host absolute target with no positive retained match gets no CC11 English fallback and no new privilege. A current web resolver must still classify the known accepting controls in its moved vocabulary; losing an actual known offer/conflict to an omitted field is a producer defect, not a compatibility fallback. A known accepting control with unknown layer context has `accept` without `responseOnly` and remains refused in the relevant optional/handler position. A malformed supplied field always fails, even when its parameters or display label look safe.

## Risks and limits

The classifier remains a conservative language/context heuristic over untrusted observed content. It cannot discover a hidden server-side consequence or prove that a deceptive control does only what its label says. Missing metadata must not be described as safe, and a commit effect floor does not supply missing consequence classes. The actionable structural improvement is removing model-authored consent as authority and ensuring any response-only exception comes from the exact host-retained target and layer. Cross-view conflict handling and resolver validation are required parts of this unit, not optional later cleanup.

Source inspection found no per-control CC11 field already transported to this consumer. The existing CC7 obstruction intent is a different policy and must remain unchanged. All current source references and named tests were read/searched; no implementation, tests, typecheck, audit, build, browser/provider call, git operation or private task-tree write was performed. Runtime behavior and compatibility remain unverified until the lead implements and runs the owning checks.
