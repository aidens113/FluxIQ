# Installed browser batch proof design

Status: source-backed design; not executed.

## Recommended proof

Use the existing installed Chromium fixture and its provider-free Core build path, with one `core.run_node` and one-member `core.run_nodes` call in the same evidence loop. Keep the same observed newsletter email input handle, text, and `submit: false` in both actual dispatches. This is the narrowest safe effect already declared repeat-safe by the domain: `web.dom.type` resolves to `effectClass: state`, `repeatSafe: true` when submit is false; submit true resolves to `commit` (`domain/src/actions/action-effect/table.ts`, `resolve.ts`). No form submit, reset, recovery, or selector rebind is needed.

1. `startInstalledBuild(extensionSession)` creates an isolated Core root with `loadEnv: false` and `modelProvidersEnabled: false`, starts the scenario Lab, installs the real native web output registry and diagnostic gateway (`apps/extension/e2e/site-reset/installed-build.ts`). Use `/scenarios/company-website/`; follow the fixture's real first-visit flow, then open the footer's "Offers and reminders" link. The fixture's public workflow identifies `main input[name="email"]` and the synthetic value `ada.synthetic@example.test` (`apps/scenario-lab/src/scenarios/company-website/qualification/newsletter-signup/workflow.ts`; `qualification/first-visit.ts`). Do not submit.
2. Pair with `installed.pair()`. Bind `bindScriptedProvider` and start `projectBuild(...).run()`; this uses the public `service.generateFlowBootstrapAdaptation` entry and public service provider binding (`site-reset/scripted-provider.ts`, `site-reset/project-build.ts`). Script the normal plan/dispatch turns, then use the page snapshot in the builder evidence to select the *current* email input handle. Dispatch `core.run_node` for `web.output.dom-type` with `{target:{handle}, text:"ada.synthetic@example.test", submit:false}` (empty consequences). Record the actual `core.run_node` evidence entry's `callId`.
3. On the next builder turn, call `core.run_nodes` with exactly `{calls:[originalCallId]}`. Do not recreate a draft call or include other IDs. Assert same definition and concrete parameters in the private captured member; assert no new draft step. The tool contract limits input to an ordered unique list of earlier successful `core.run_node` call IDs, reruns exact frozen original inputs, and adds no Flow step (`runtime/llm/node-reruns/tool.ts`, `prior-call.ts`).
4. Require final build proposal; inspect installed gateway counters around just these two member dispatches: two `web.dom.type` entries, two successful gateway result summaries, two distinct action-command IDs by `distinctActionCommands()`, no gateway errors, no form submission/navigation, and the email value unchanged after the second dispatch. Preserve only counts/statuses, not page content or IDs.

## Why this is the real gate

The service creates loop authority from the live native runtime, binding generation and Flow scope (`runtime/service/flow-bootstrap-commands/execution-authority/create.ts`; `runtime/llm/prior-nodes/authority.ts`). The batch loop offers `core.run_nodes` only when the authority and a prior successful `core.run_node` are present; it re-reads ordinary tool admission and the live authority per member (`runtime/llm/prior-nodes/loop.ts`, `admission.ts`). It executes through the existing `runCall` and normal member runner, keeping actual receipts private and counting only `main: receipt` as executed. D3's frozen contract additionally requires an accepted producer report of the fresh selected dispatch receipt before a member can count as executed; absent proof remains unproven. Do not supply a test-side `rerunAuthority`, mock executor, manufactured report, or direct importer action.

## Expected scope and constraints

Exactly two main `web.dom.type` dispatches should be counted: original plus one batch member. One envelope is not a main action; it must not increment member count. No model/provider network call, reset, repair, recovery, extra member, permission relaxation, or whole-Flow judge is involved. Per-member tool admission, authority/effect checks, cancellation, time and existing purse limits still apply; the batch adds no numeric cap. The existing Playwright entry is `pnpm --filter @fluxiq-web-extension/extension test:e2e -- e2e/site-reset/tests/<new-spec>.spec.ts` (script builds before invoking Playwright, so only run after root authorizes that validation).

## Evidence boundary / unresolved source check

`installed-build.ts` already exposes the actual site action types, result status summaries, distinct command-ID cardinality, and gateway errors without exposing IDs. D3's host-only `reportDispatch(capsule, dispatch)` is not a test hook: the producer must call it from the actual selected attempt observer. Before implementation, confirm the frozen D1/D0 wiring in the refreshed installed SDK forwards the producer's actual two receipts through that observer. If not, stop with that precise missing wiring; do not add a local bridge. No test, browser run, build, source edit, or provider invocation was made for this design.
