# P8 host identity discovery

## Finding

The downstream has a source-less reacquisition building block, but the retry hook is currently only enabled for a looked-up handle. `webNodeLookedUpReacquire` takes the action’s saved `parameters.element` fingerprint, reads a fresh page, rebuilds candidate fingerprints from that page, calls the same matcher, then returns the selected fresh selector and fingerprint in parameters. It intentionally does not return or persist a handle. At present it returns no finder when `handle` is absent, when `element` is absent, or when `parameters.target` is an object (state-bound target). The call site supplies `webPlanFirstTargetHandle(written)`, so an authored literal target has no reacquire hook through this path.

A bare literal `selector` is an address only; it provides no stable identity. The reusable identity is `parameters.element` as a `WebAutomationElementFingerprint` (including signals built by `webPacketElementFingerprint`). Model-authored element literals are refused by plan resolution; hand-authored/saved literal selectors may still execute, but if they have no saved fingerprint they cannot be safely reacquired. A source-less extension should therefore match only when a stored fingerprint exists, and return unmatched/unavailable otherwise; it must not fall back to the selector, position, or stale handle.

## Flow, matching, and guards

- Host seam registration: `domain/src/runtime/host-runtime.ts:294` delegates `reacquireTarget` to `webAutomationReacquireTarget`; that matcher’s public shape requires lineage, source, stale value, and candidates (`domain/src/runtime/target-reacquire/reacquire-target.ts:19`). Its control path selects `webReacquireElement` only for an output lineage (`:22`).
- Shared element matching: `domain/src/runtime/target-reacquire/element-match.ts:44`. It requires at least two identity signals; every signal both sides carry must agree; zero matches means `gone`; multiple matches mean `unmatched/ambiguous`, except a unique matching record can break a tie. Selector/xpath/position/handle are not matching signals. The matcher returns the fresh candidate itself.
- Existing browser reacquire owner: `domain/src/runtime/llm-evidence/node-run/retries/looked-up-reacquire.ts:38-45` currently requires a handle and stored `element`, and excludes object `target` bindings. It limits candidates to the action’s frame (`:45`, `:64-75`), fingerprints current evidence with its current selector (`:69-75`), calls the matcher, and updates the run’s current page binding (`:51`). On found it replaces selector and element with the fresh candidate while preserving the remaining action parameters and `readsWords` (`:54-57`). `WebLlmSnapshotBinding` owns fresh evidence and selector bindings (`domain/src/runtime/llm-evidence/sanitize.ts:97`); `webPacketElementFingerprint` is the packet-to-fingerprint builder (`domain/src/runtime/llm-evidence/packet-fingerprint/from-packet.ts:45`).
- Retry hookup is in `domain/src/runtime/llm-evidence/node-run/run.ts:393`; it passes the already-resolved dispatch parameters and the fresh-page reader. `domain/src/runtime/llm-evidence/node-run/retries/reacquire.ts:29-57` turns found into dispatch with fresh parameters, gone into a nonretryable target-gone result, and unmatched/unavailable into Core’s retry outcome. Preserve the existing retry timing and effect/landing protection: this callback is passed to Core’s retry coordinator, and must only be reached after Core’s established stale-target/no-act gate. A fresh identity lookup must never authorize repeating an act whose effect is ambiguous or may have landed.
