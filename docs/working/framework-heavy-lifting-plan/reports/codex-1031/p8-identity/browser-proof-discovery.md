# Browser proof discovery: source-less identity refresh

## Finding

A provider-free installed-extension proof of the new Core hook is not presently honest to promise from the proposed `social-network-feed` selector-shift setup. The real fixture has the needed site-authored mutations: `apps/scenario-lab/src/scenarios/social-network-feed/client/unit-script.ts` implements `Hide post` by replacing the post article's children and `Undo` by restoring them; owned-post `Actions -> Move to trash -> Move` removes the article. `markup/unit.ts` renders repeated post controls inside positional `role="article"` feed records. Removing an earlier article can change a later control's generated address, but that address change must be observed in a future run before claiming it.

More importantly, a selector miss/neighbor hit does not establish three browser failures. `apps/extension/src/content/action-runtime/resolve-target.ts` tries the selector and applies the recorded-record gate before counting/acting; on a miss it continues through fingerprint/name lookup and scored candidates. The existing `identity-resolution.spec.ts` proves that selector drift is routinely recovered locally (e.g. the crossborder title-only swatch resolves as `strategy: "fingerprint"`). For feed actions, a saved target fingerprint also carries its containing record context, so a post's old positional selector can miss or hit another post while extension-local matching recovers the same post or vetoes the neighbor before Core receives a failure. We have no observed natural fixture state in which this target produces three genuine, unacted stale results and then becomes recoverable by Core. Do not claim the host hook ran based on a changed selector alone.

## Strongest honest browser alternative

Use a future provider-free installed-extension spec to demonstrate the real lower-layer result and the security negative separately: save a source-less control handle in post A, use the fixture UI to hide A (its controls are replaced while post B keeps an identical control), then attempt the saved action and inspect both posts' actual state. Assert that no action lands on B and describe the result as extension-local record gating/recovery, not Core-hook acceptance. Use Undo or the fixture's real trash confirmation only as a separate site-state setup where needed. A positive Core-hook acceptance still needs the native Core tests against actual hook invocation/capture protocol; a browser integration that cannot naturally deliver its failure precondition is not that proof. No failure injection, DOM fabrication, action monkeypatch, or gate bypass is justified.

## Existing harness and evidence points

- `apps/extension/e2e/site-reset/index.ts` exports `startInstalledBuild`, `bindInstrumentedRuntime`, `projectBuild`, `pageHandle`/`rowControl`, and diagnostic helpers. The installed harness imports `FluxIQ`, `AutomationStudioNativeNodeRuntime`, the web domain registration/output-node bundle and runtime permissions/capabilities, `startScenarioLab`, and the real extension `ExtensionSession` fixture.
- `startInstalledBuild` creates Core with `loadEnv: false` and `modelProvidersEnabled: false`, registers `createWebAutomationOutputNodeManifest()` plus `createWebAutomationOutputNodeImplementationBundle()` with the native runtime, starts the real client gateway and scenario Lab, and opens a page in the installed extension context. Pairing is through the extension UI and approved local gateway. The harness binds no model provider.
- The registered output used by existing specs is `web.output.dom-click`, with `{ target: { handle } }`; e.g. `photo-toggle.spec.ts` builds this output for a click. The gateway's `commanded` callback records `server.execute_action` action types; `InstalledBuild.siteCommands()` records Core-to-site action types, `actionResults()` counts returned results, and `gatewayErrors` records transport failures. `bindInstrumentedRuntime` observes real start-state reads, permission declarations and tool outcomes, and click dispatch count without changing execution. Per-item state must be read from the fixture's site-owned state/control surface before and after; status alone is insufficient. Keep diagnostics to digests/counts and do not print page values or runtime identifiers.
- The referenced one-spec command, once that spec exists and implementation is frozen, is: `pnpm --filter @fluxiq-web-extension/extension exec node --no-experimental-strip-types node_modules/@playwright/test/cli.js test -c e2e/playwright.config.ts e2e/site-reset/tests/native-source-less-target.spec.ts --workers=1`.

## Limits

This was source inspection only. No browser, check, test, build, API, provider, panel, or runtime-state operation was performed. The exact changed selector and whether any target can naturally reach three failures remain unverified; the proposed positive Core-hook browser proof is therefore infeasible to claim on current evidence.
