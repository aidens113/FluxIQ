## Established gaps and existing behavior

- **Prefix replacement remains missing.** `R/llm/context-window.ts:113-147` recomputes historical entries backward and replaces old views only after a successor exists. This rewrites bytes previously sent whole; its current comment is stronger than the implementation.
- `R/llm/evidence-loop/tests/request-prefix.test.ts:33-37,111-142` explicitly permits this: the asserted prefix ends *before* the former current view. The discovery report's statement that replacement prefix behavior already exists must be narrowed accordingly.
- **Full view/rows are already retained independently.** `R/llm/decision-context/view-groups.ts:19-40` groups top-level page keys separately from each holder's rows. `context-window.ts:127-147` replaces only within a group; a page-only result does not erase the last read's rows. Preserve that behavior and recall, rather than truncate either view.
- **Route deltas remain missing.** `R/route-state/build-routing.ts:191-211` serializes each situation's entire screened `state`; placement is already append-only. `R/llm/evidence-loop/tool-execution.ts:117` merely carries the execution's full route state and is not the projection owner.
- **Callable-only tool variants already exist.** `R/llm/evidence-loop.ts:613-640` computes the actual eligible/wrap-up offer and constructs its schema from `offered`; `evidence-loop-decision.ts:400-409` maps only those tools. `provider-task/output-schema.ts:80-90` embeds that same decision schema. Do not introduce a second callability implementation.
- Here “callable” means currently offered tool. Separately, `subflow-candidate/builder-loop.ts:326-327` leaves `plan` in a callable *subflow interface* scope's schema although `scoped-submission.ts:304-309` requires script. That is a distinct schema cleanup, not evidence that an unavailable tool variant leaks.
- **Identical-node batch remains missing behavior.** `R/llm/node-tools/loop-tools.ts:29-43` installs the part-run binding, and `run-flow.ts:43-68` accepts a contiguous `from/to` range, not an explicit list of identical original calls. `R/llm/evidence-loop.ts:400-451` executes/accounts one call; neither seam implements requested list execution with per-original result-code stops.

## Stable contracts to freeze before dispatch

1. Historical view projection is immutable from its first appearance: preserve non-view keys; replace each declared group's members immediately with an immutable reference identifying its original `callId` and group. Do not use a future successor's id as that reference. Keep raw evidence untouched for recall, signatures and execution.
2. Append one `core.current_view` trailing entry after all historical results (before history/draft/budget), holding the latest *whole* payload of every declared view group, its original source call id and holder. Each current page/group and current row array appears once, without caps, summaries or samples substituted for it. A page-only update leaves the last read group intact. Keep `core.current_flow` in the dynamic tail too.
3. Prefix guarantee covers every shared immutable result in serialized provider messages when the offered schema/head is unchanged; dynamic trailing entries may differ. Offer changes retain the existing explicit exception. UTF-8 bytes, not JS character offsets, are the acceptance metric. Recall payloads must follow the same immutable-history/dynamic-tail rule.
4. `core.route_state`: first screened situation is a full baseline; later entries carry changed flattened state keys plus explicit removed keys and a base situation id. Compare canonical JSON values, distinguish null from missing, keep prior entries immutable. Derive this only for model projection; full observations/context/signatures/effects remain full. Screen before diffing so a secret becoming withheld produces removal, never a stale visible value.
5. Proposed batch input is `{calls:[<prior callId>,...]}`: an ordered nonempty list of already executed successful `core.run_node` calls in this loop, each with a frozen original concrete input and result-code baseline. No parameters, safety labels, additions, bindings, writes, flow runs or nested batches can be supplied. Do not infer success from absent `ok` alone; use the existing execution reader and successful receipt semantics. Reject duplicate/unknown/ineligible members before any execution.
6. Keep a loop-owned prior-call registry, including successful exploration calls never added to the draft. A call id alone is not authority: freeze resolved node id/version, concrete `ranWith`/original input, result code and trusted effect source; invalidate on changed registry/definition/authorization. No output/row rebinding or implicit page reset/repositioning in a batch.
7. Resolve safety anew before each member from trusted runtime data. Admit `observe` with no permission consequences, or non-commit `state` only with explicit trusted `repeatSafe:true` and no permission consequences. Reject unknown/malformed/commit, unresolved conditional floors, any observed/declaration evidence of lasting effects, uncertainty, and stale authority. Model `consequences:[]`, node metadata and permission approval alone never establish repeat safety.
8. Trusted resolver seam: optional loop callback `resolveRerunEffect(nodeId, concreteParameters)` returns the existing `AutomationStudioResolvedActionEffect`; absent means unavailable batch. Service wiring must call `AutomationStudioNativeNodeRuntime.resolveActionEffect` on a canonical execution node, not resolve a model catalog entry. This preserves generic `builtin.policy.action` output floors (`native-node-runtime.ts:80-93`). No public domain/client wire contract is required.
9. Execute sequentially through the original fully wrapped `core.run_node` executor and existing rerun admission, retries, receipts, cancellation and uncertain-effect handling. Never call `nativeRuntime.execute` directly. Stop after the first final failure, unreadable/throw/person-needed/uncertain result, changed result code (including missing versus present), lost eligibility, exhausted tool/time/purse allowance or guard refusal. Retain all earlier receipts and the stopping result; never dispatch later members.
10. One model decision may request the list; each actual member consumes normal tool-call/evidence accounting and shares the original purse. No new provider is attached, no per-member purse, and the synthetic envelope is not a second executed node. Batch receipt names requested/executed/skipped calls and the stopping index/reason; individual full evidence enters the ordinary window and keeps privacy/control metadata handling.
11. Repeat identity is the ordered canonical list of resolved node ids/versions and frozen inputs, plus the existing world/authority context, not model-chosen call ids alone. Preserve individual protections and also record/check the list once; internal members must not make the batch look like a new list merely by moving an epoch. Changing aliases or JSON key order cannot bypass it; changing order genuinely changes the requested list. No batch can establish judged whole-Flow success.
