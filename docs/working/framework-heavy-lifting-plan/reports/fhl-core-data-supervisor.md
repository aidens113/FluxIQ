## Outcome
Done. Main finding: the dataset and purse sides are already mostly Core's, and the model holds a thin declarative layer on top. The remaining model load is in four places.
1. The model writes a `recordOutput` (schema, columns, `process`) per reading step. Core owns the semantics (`C/process/process-rows.ts`) but not the defaults.
2. The model writes a one-line `summary` with every tool decision, which is the chat's "reasoning" line (`R/llm/evidence-loop-decision.ts:448-457`, `R/activity/decision-reason.ts`).
3. The supervisor hand-writes dispatch briefs and completion objects that Core already holds.
4. A dead brief is only caught by a stall guard that counts "nothing new", so a brief that keeps reaching new pages is never caught. This is the 50-decide waste in `fhl-step-workload.md`.

The purse already is one Core authority; the model only chooses to lower a brief's allowance. Section 4 of the ranking is where Core can recover the most money and time.

## Top (b) changes ranked by effect

### 1. Detect a dead brief early by the repeated unmet requirement, not by pages
- Evidence: step-workload lists builder 1 (steps 8-104, 49 decides, about 2.08M input tokens) stopped for "repeating calls without progress", mostly 26-104 chasing a "witnessed destination" for one press. The resend (106) ended on an unknown tool. About 50 decides, about $0.04, about 100 s, about 45 percent of model spend. This is larger than all of the firm and soft bookkeeping folds combined (step-workload "Estimate").
- Cause (my reading of `no-progress.ts`): the counter resets on `cleared()` when the loop "learned something" and counts an applied call as progress when `stateAfter` is a page not seen before (`no-progress.ts:181-186`). Moving across pages to try another way keeps the count at zero, while every submit or test returns the same trial feedback.
- Change: add one more failure ledger to `AutomationStudioLlmEvidenceNoProgress`, keyed by the unmet requirement (the trial or refusal issue code plus the target subject, for example `witness_missing` for one act id), not by draft signature or page. `refusedAgain(signature, issueSet)` already exists but forgets on any draft change (`no-progress.ts:191-196`). The new rule: the same code for the same subject N times (3) across distinct drafts is a dead requirement. Core then does three things in order: (1) at the second repeat it injects the existing stall redirect with the code's exit named (the closed exit the debug notes propose, `gate_unsatisfiable`); (2) at the third it ends the brief as `blocked` with that code as its return reason; (3) the supervisor receives it with `earlierAttempt` already carried (`dispatch-tool.ts:456`) and the resend of an unchanged brief is refused without a model call (`project.repair_unchanged` exists, `dispatch-tool.ts:461-473`; move the check before the decide).
- Generic contract a client supplies: a trial or refusal issue carries a stable `code` and a `subject` id. Both already exist as issue codes and act/part ids. No site terms.
- Wrong choice caught: a requirement that is slow but solvable would be cut at 3. The cut ends the brief `blocked`, not the build, and the supervisor's repair-first rule (`completion.ts` "repair-first", `heldForRepair`) still gives it one changed brief. Pick N from replay: count how often the same `(code, subject)` repeats three times in the 8 debug-note runs and a run that then went on to pass. I did not run that replay.
- Expected effect: for the t563 run, builder 1 would likely have stopped near step 40, not 104 (inference from the step list 26-104 repeating one theme; the exact repeat count of the code was not checked). That saves about 25 to 30 decides, about $0.02 and 50 s of 248 s model time.

### 2. Auto-complete a brief and the build on a yes, and default brief fields
- Evidence: 12 firm test-after-submit decides, 2 complete decides, 1 unchanged redispatch (step-workload table, 20 firm decides, $0.0131, about 41 s). The supervisor copies `revision`+`digest`, `failingReceipt` and the `complete` object back (fhl-core-surface items 1-3, 5).
- Change: Core completes a builder's brief when its judge says yes for the latest revision. For a one-subflow plan the supervisor's complete is Core's too. Defaults in S2: `parts`, `kind`, `failingReceipt`. A `test: true` option on submit, or Core running the subflow test on a clean submit, removes the 12 test decides.
- Caught if wrong: a stale revision or a digest mismatch is refused as today; the model keeps an `ended: blocked|partial` path.
- Effect: 20 of 118 calls, $0.0131 of $0.0861, about 41 s of 248 s model time (per step-workload estimate A). Overlaps the "folding" report; I count it once.

### 3. Dataset defaults declared once from the task-spec part
- Evidence: the part already declares `answer: {kind:"records", columns}` (`tools.ts:34-38`). The builder then writes a `recordOutput` with schema, id, label, columns and `process` (`record-output.ts` synonym tables exist because "it refused more builds than any reasoning mistake did", header lines 3-16).
- Change: Core pre-fills the record output from the part: dataset id, label, schema from the columns (type `string` unless the column name is declared numeric or date by the client), `process.columns` set to the asked columns in order, default dedupe (whole row, or the client's declared `rowIdentity`), write mode `append`. The builder only adds `where`, `sort`, `limit`, and the row bindings. This extends what `authoring/record-output.ts` already does from the builder's own columns, up one level to the plan.
- Generic contract: client supplies per-listing-node `rowIdentity` (field ids of its row type), per-field `valueType`, and a `fields` list with a source reference. A desktop or API client states them for its own row type.
- Caught if wrong: `requested-output/missing.ts` already holds a yes when no records are stored; add the missing-column check from `kept-without-asked-column.ts` on every asked column (already present for column cuts); the judge sees the pre-filled schema as the Flow's shape.
- Effect: no measured call count. The measured evidence is refusal counts in the campaign cited in `record-output.ts` header and `record_output.*` / `record_schema.*` codes, so I rate it a reliability win, not a dollar win. Not quantified here.

### 4. Count requests as typed row counts and settle them in Core
- Evidence: fhl-core-surface item 18; the examples "three newest", "at most 300", "14 of 280". `answer` has no count today (`tools.ts:34-38`), so the judge decides "a count that cannot match the request" as it did in the 7 judge pairs of step-workload (23.9 s, $0.0026 for the twins, plus defects in cell shape).
- Change: `answer.rows: {count|atLeast|atMost}` in the plan, taken from the quote by the supervisor. Core compares `kept` and `limit` and hold-checks a yes the same way `requested-output/held-yes.ts` holds one.
- Caught if wrong: a wrong number copied from the quote is visible in the quote span, which Core already verifies verbatim (`task-spec.ts` header). Mismatch is a finding, not a verdict.
- Effect: settles the cell-shape and count defect class before the judge (4 of 14 judge calls were "largely settleable", step-workload judge table: steps 189/190, 198/199, 228/229) and removes the twin judge (7 calls, $0.0026, 24 s).

### 5. Chat reasons: compose for bookkeeping decisions, keep the model's for choices
- Evidence: `evidence-loop-decision.ts:448-457` already tolerates a missing `summary` and fills `<kind> <toolId>`. Core already composes titles, cards and the ending. Bookkeeping decides (test-after-submit, complete, redispatch, folded re-runs) are 20 of 104.
- Change: when Core folds a step (item 2), it posts the chat line itself from the record (for example "Tested revision 3: passed" from the receipt). The model's `summary` stays for first-time looks, runs and repairs. The extension chat still shows every step with its reasoning (MEMORY rule): a Core-written step shows Core's reason, which names the same record the step acted on.
- Caught if wrong: nothing to catch; text only. Keep Core's held-narration rule (`narration.ts`).
- Effect: output tokens only (27,009 output tokens over the whole run, $0.0162); not a latency win by itself. Small. Do it with item 2, not alone.

### 6. Ending reason from the record when the build succeeds
- `ending-told.ts` already screens and trims the supervisor's reason. A done ending needs no supervisor prose: Core says which parts are done and which trials passed (`record-told.ts`). Saves one supervisor decide's output; small.

## Risks
- Item 1 can cut a brief that a few more tries would have rescued. Mitigation: end only on the same `(code, subject)` across distinct drafts, end `blocked` (repairable), and tune N by replay of recorded traces (eight debug notes plus the t563 run). The existing guard's own header shows the same lesson: at 3 it was too tight, at 24 it never fired, 8 was read off a trace (`loop-limits/evidence-loop.ts:42-80`).
- Item 2 hides a bad yes: the judge's yes becomes a completion without the supervisor looking. Mitigation: keep the build-yes hold and the lone-yes confirmation (`R/result-verification/build-yes-hold`, debug-notes s.2) between the judge and the completion.
- Item 3 pre-filled schemas may carry a wrong column type for a client that mislabels a field. Mitigation: type only from the client's declared `valueType`; default `string`, never guess from a column name.
- Row identity defaults can merge distinct rows when a client declares too small a key. The all-empty rule (`row-identity.ts:11-18`) and the per-condition account remain; the account's `duplicates` count shows the merge.
- Teaching to the test: every example in new contract text must use a different kind of site from the realistic scenarios (library, club, invoices), as the existing format text does.
- Counting with `answer.rows` depends on the supervisor copying a number from the quote; if it adds a number the person did not state, Core's verbatim-quote check on the span catches it only if the number is inside the quote. Require the count to be derivable from the quote text.
