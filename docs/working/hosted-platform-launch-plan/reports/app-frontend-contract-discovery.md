# Standard app frontend contract: first implementation unit

Outcome: Done (read-only discovery). Recommended first unit: **immutable app manifest + durable workspace installation/grants + fresh authorized operation resolution**. It can be completed and tested without pretending the current owner-only FluxNode API is an app API or returning a fake successful execution. Registered-app delegation and durable invocation admission are required before the custom frontend demo.

Read scope: Core Current State, the paired plan's Standard Custom-App Frontend Contract, source contracts/SDK, FluxNode HTTP/runner, key-session authority, fixed extension connect and commerce admission. No `dist`, builds, tests, servers, browser, git or paid calls were used. Only this report changed.

**Durability already implemented versus still needed**

`FluxNodeRunRegistry` and `FluxNodeRun` keep run ids/state/results, event arrays, pending answers, resume handles and live observers in memory. A disconnected stream leaves the current run going and can replay by sequence while that process survives. This is implemented local execution behavior, not a durable accepted run/events contract.

There is also important existing durable execution protection to preserve. `service/fluxnode/act-scope/idempotency-keys.ts` persists the owner/project request binding to an opaque execution scope through `ProgramJsonStore`; request projection excludes secret values. `execution-task.ts`, `execution-targets.ts` and `execution-owner.ts` preserve task/target bindings and exclusive ownership, and scoped lasting-act memory prevents repeating uncertain effects. Learned Flows, datasets and pins can survive. Do not replace these with a second app retry/run engine, and do not claim that their existence persists an app receipt or old `FluxNodeRun` event log. A restart may retain an execution's lasting-act identity while the previous public run id/events are no longer addressable.

**Recommended stable seam to freeze before dispatch**

Names below are proposed, not existing exports. Use additive `@fluxiq/contracts/apps` and later `@fluxiq/sdk/apps`; keep the Node SDK root and `/api/fluxnode/v1` open-mode guards compatible.

- `AppManifestV1`: explicit schema/protocol version, publisher/app/version and immutable package digest; frontend entry and exact allowed origins/redirects; named operations with existing `JsonTypeSchema` inputs/results; requested data/secret/network/consequence permissions; required runtime/callback/environment capabilities; supported protocol/runtime versions; explicit update policy. Separate canonical manifest digest from the digest of package/assets, and exclude a digest's own field from its canonical input. Publisher provenance never grants access.
- Each operation names an immutable **installed backend binding**, pinned to a FluxNode spec/pipeline/Flow version/hash verified by the installer. Browser input is only typed operation arguments and invocation identity. It cannot supply executable source, `authSessionId`, a role, a model secret, target overrides or a payer/workspace authority claim. Data-read operations and paid execution operations are distinct kinds.
- `AppInstallation`: opaque server id, current workspace, pinned manifest/package version/digest, approved grant set, explicit environment/target binding and server-resolved payer policy, installer/audit identity, revision/generation and active/revoked state. Updating a package never widens a grant automatically. An explicit authorized install/update validates the artifact and any new permissions; old grants/tokens remain bound to their approved pin/generation.
- `AppOperationAuthority`: a required trusted host port resolves the current authenticated user/service identity and delegated app session, verifies workspace membership/IAM, installation/pin/generation, exact request origin, declared operation and all grant intersections, compatible target/environment, and payer/entitlement policy. Missing authority, storage error or unsupported execution capability refuses. Local/self-hosted use supplies an explicit authorized host composition; it never silently becomes paid cloud execution.
- `resolveAppOperation(context,{installationId,operationId,inputs})` returns a checked **operation resolution**, including the server-owned target and authority bindings, or a stable refusal. Context comes from authentication/host adapters, not the JSON body. It is not a portable bearer, accepted-run receipt or completed execution. Revalidate its current authority at dispatch/resume and protected data/stream operations; a resolution cached before revocation is not durable permission.
- Browser auth is registered-app authorization-code/PKCE with an exact registered redirect, expected state and origin, app/install/grant binding, short-lived audience-scoped access and revoke. BFF/delegated server credentials remain server-side. Anonymous access is an explicit published-data or narrowly publisher-funded server policy; omit it from the first unit rather than accidentally defaulting it on. Embedded support, if later added, requires exact origin/source and constrained message schemas on an untrusted-app origin, never the panel cookie.

The first unit should implement manifest validation, authenticated install/revoke and fresh operation resolution against real isolated persistence and trusted authority ports. It should **not expose an invocation endpoint or return `accepted`/`running` using an unimplemented executor**. This is a complete authorization/configuration kernel with honest capability reporting, not the completed frontend demo.

A1/A2 are the recommended next bounded implementation. Their contracts must freeze before the other owners start; shared export/host composition files remain serial with the lead. B/C can then use disjoint subtrees until their explicit adapter boundary is integrated. Public package additions need the repository's normal compatible versioning and paired-consumer checks, not an incidental registry publish during discovery.

Suggested future commands, **not run**: scoped `pnpm.cmd --dir packages/contracts exec vitest run src/apps/tests`; Core owner tests under the new `src/platform/apps/**/tests` and `src/server/app-api/**/tests`; existing FluxNode `tests/{idempotency,act-scope,run-registry-shutdown,secret-invariant}.test.ts` and HTTP `server/fluxnode-api/tests`; SDK new apps tests plus affected existing `src/client/tests` and session tests. Add an explicit browser-platform bundle check for the new public entry. Rebuild shared exports and run package types/structure only after owners reach a stable batch. Real browser demo acceptance uses the downstream's permitted realistic fixtures and saved-Flow continuation proof; no paid provider is needed for contract/refusal/idempotency conformance.

**Dependencies before a real demo**

Registered-app identity and delegated auth; trusted installation/artifact/upgrade lifecycle; current tenant/install/origin/operation authorization; app-scoped dataset/file access; real execution/worker/callback capability binding; explicit server payer and paid dispatch/metering when cloud compute is chosen; durable receipt/event recovery; browser-safe SDK export. A local callback or developer check cannot be assumed to survive a refreshed browser: declare a real server/local worker requirement and refuse unavailable execution. The current fixed extension PKCE, enrolled SDK sessions and commerce eligibility do not together implement these missing seams.
