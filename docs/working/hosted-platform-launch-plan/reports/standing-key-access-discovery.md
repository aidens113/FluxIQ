# Standing run key access: admission and custody discovery

Outcome: Done (read-only discovery). The current standing path does **not** supply the durable grant/redemption identity needed by the frozen `SecretKeyUsePrincipal.kind: "standing"`. Removing its held-panel dependency by constructing a principal from user/project/flow ids would create authority that the current admission does not prove. No source changed and no tests/builds ran.

**Exact existing path**

1. A saved Flow's `metadata.trainingModeSettings.resultCheck.authorization` is parsed by `automationStudioResultCheckAuthorizationFromMetadata` in `framework/automation-service/service/flow-settings/result-check-settings.ts`. `runtime/result-verification/check-authorization/contracts.ts` defines key id, authorized user, an `unlockSessionId`, total/per-call estimates, granted/expiry times, and an optional explicitly enabled repair clause. There is no grant id, generation, revoked state, workspace identity, run binding or redemption receipt id.
2. `resolveAutomationStudioRuntimeAdaptationContext` in `service/runtime-adaptation/resolve-context.ts` reads that settings snapshot and the most recent 100 run summaries. `runtimeTrainingBudgetStateFromSummaries` in `context.ts` sums `run.tokenUsage.estimatedCostUsd`. This is the tally supplied to both standing redemptions; it is not a durable grant account or reservation ledger and is not filtered by `grantedAtMs`.
3. `automationStudioRunResultCheck` in `service/runtime-adaptation/result-check.ts` asks the check schedule first, then calls `redeemAutomationStudioResultCheckAuthorization`. This pure function checks the supplied task kind is `loop_verification`, key/unlock ids are nonblank, limits positive, expiry in the future, and the supplied remaining estimate covers a whole call. It returns key/unlock/user ids and an estimate ceiling. It neither loads nor consumes any stored grant.
4. `resolveAutomationStudioResultCheckProvider` tries an admitted caller provider first. Otherwise it forwards `{projectId,flowId,keyId,unlockSessionId,authorizedByUserId,maxEstimatedCostUsd}` from the check snapshot. The standing authorization's own expiry and task purpose do not reach the host resolver. The host gets no opaque evidence that this request came from an admitted run.
5. `resolveAutomationStudioUnattendedRepairAuthority` in `service/runtime-adaptation/repair-authority.ts` uses the same supplied authorization and tally. `redeemAutomationStudioUnattendedRepairAuthorization` checks repair enabled, expiry, limits and remaining whole-repair estimate. The returned task kinds are fixed: `runtime_diagnosis`, `evidence_tool_decision`, `runtime_patch`. The recovery provider wrapper refuses other task kinds and carries no consequence permission. It forwards the same host scope shape as verification, so the host cannot distinguish repair from `loop_verification` today.
6. `programs/_shared/runtime.ts`'s `resultCheckProviderResolver` loads the Flow only to resolve model/provider metadata, then creates `createAutomationStudioResultCheckProvider` with the supplied scope. It does not reload/validate the stored standing authorization or current payer authority. Its ports still mint a held-session reveal.
7. `runtime/result-verification/check-authorization/reveal.ts` checks project/Flow equality, rejects a `paired-client:` unlock, checks enabled model/provider compatibility, calls `createSessionRevealAuthorization` with the supplied unlock/user, checks returned key/seal version, then consumes the reveal. The outgoing body must not contain the credential. The held unlock currently supplies the missing authority boundary; removing it without replacement would widen access.

**What exists and what is missing**

- The metadata record is durable with the Flow, but no authenticated standing-grant issuance/renew/revoke service was found in Core/web production writers. `programs/automation-studio/api/handlers/flows.ts` and `flow-settings-requests/{update,stored-check-authorization}.ts` deliberately preserve the existing record and reject client substitution. `api/tests/flow-check-authorization.test.ts` seeds the stored record through direct `service.saveFlow`; its tests prove injection refusal, not an issuance lifecycle.
- Re-running either `redeem*.ts` predicate does not consume anything twice: neither consumes anything once. It only rechecks a supplied snapshot. There is no durable consumed-grant receipt whose current state could be checked again at key mint and reveal consumption.
- There is no current stored-record match, generation/revocation check, account-enabled check, current workspace membership/IAM check or actual run ownership/purpose binding in the standing reveal path. Deleting/replacing an authorization while a run retains its adaptation context does not itself invalidate that captured scope. Expiry can pass between the initial predicate and the actual provider call without a new standing-expiry check there.
- The 100-summary estimated-cost tally does not establish a lifetime total for a grant; old spend falls out, prior-grant spend is not separated, and simultaneous runs can each pass against the same old tally. No reservation/settlement or idempotent spend identity was found here. Keep existing estimate ceilings, but do not describe them as a concurrency-safe billed grant budget.
- `AutomationStudioInstructionAuthority.assert` checks that saved Flow instructions/task ownership exist (including parent ownership for subflow graphs). That is useful execution admission, not a credential grant or a current payer/workspace authorization.
- `programs/_shared/press-grant/PressGrantStore` is unrelated: an in-memory, panel-session-bound, one-use, 60-second confirmation for one destructive endpoint/payload. It is not a durable standing authorization and must not be stretched into one.
- The new frozen key-access authority correctly returns null for `kind: "standing"` in `_shared/key-access/authority.ts`. Preserve that refusal until a real standing validator exists. No null-session or synthetic `trusted-client` conversion is safe.

**Smallest safe integration partition**

The immediate adapter edit is small, but its authority prerequisite is not yet implemented. Keep the existing refusal until the lead provides a real host-owned grant/redemption validator; this report does not authorize or implement a new grant system.

| Owner partition | Required work |
| --- | --- |
| Grant/admission prerequisite | Define authenticated grant issuance and explicit renew/revoke over the stored Flow authorization, with a durable server-owned identity/generation. Bind proven payer, immutable workspace/project/Flow/key, allowed purpose, expiry, and actual current identity/IAM. Establish a run/call redemption receipt and budget reservation/settlement identity if claiming the stored total is a hard grant limit. Legacy metadata requires explicit trusted adoption/migration; a digest alone does not establish who authorized it. |
| Standing runtime adapter | Own `runtime/result-verification/check-authorization/{contracts,provider-contract,redeem,repair,reveal,provider}.ts`, settings reader, and `service/runtime-adaptation/{result-check,repair-authority}.ts` plus their adjacent tests. Carry the actual grant/redemption reference and purpose into provider scope. Keep schedule choice, verification-only purpose, explicit repair clause/task kinds, model/key matching and ceilings. Replace held-session reveal with `access.createUseAuthorization` only for an already validated receipt. Do not derive an authorization id from the old unlock id or arbitrary Flow ids. |
| Host authority/binding | Lead owns `_shared/key-access/authority.ts` and `_shared/runtime.ts` standing resolver. Validate the real reference against fresh durable grant/receipt and current project/Flow/run, key/payer, purpose, expiry, account/workspace/IAM and revoke generation at mint **and consume**. Hosted tenants must use primary identity and tenant membership; an isolated tenant identity directory is not the source of primary account state. Keep one-use key release and seal-version checks. |
| Budget/execution lifecycle | The grant owner supplies repeatable read validation of an admitted reservation/receipt, with separate idempotent consume/settle transitions. A validator called several times by `SecretKeyAccess` must not reserve or spend again. Preserve actual task purpose and the existing billing/spend ceiling through the provider/recovery boundary; verification and repair share the intended purse but not permissions to cause lasting effects. |

Recommended narrow host port, **not frozen API**: a `validateStandingUse` callback receives the frozen standing principal and requested key plus trusted run/redemption context, and returns current verified owner/expiry only after looking up the real durable reference. `authorizationId` must identify that actual server-owned grant/receipt, not merely label a metadata object. If the grant and per-call reservation have different identities, carry both in the trusted receipt/context rather than overloading a user-supplied string. The callback is non-consuming and safe to call repeatedly; redemption/reservation happens through its owning service once. Nothing in the current scope can provide that implementation yet.

**Recommended acceptance checks**

- Runtime contract/reveal: provider-free tests beside `check-authorization` proving an admitted current standing receipt releases a key after panel logout/restart without borrowing a panel or paired-client unlock; exact user/workspace/project/Flow/key/purpose/run mismatch, invented ids, unknown grant and obsolete generations refuse before provider dispatch. Keep key-version and outbound-credential guards.
- Lifecycle: grant disabled/removed/renewed, account disabled, membership/IAM removed, key disabled/rotated, owner offer withdrawn where applicable, and expiry racing both asynchronous mint and reveal consumption each refuse. Ordinary panel logout alone does not revoke a legitimate standing authorization. Historical metadata is not silently promoted into a new grant.
- Purpose: verification funds only `loop_verification`; repair requires its explicit clause and funds only the three current repair task kinds. Neither grants consequence permissions or funds arbitrary exploration/building. The host sees and checks the same purpose the provider wrapper enforces.
- Budget: simultaneous run admission cannot reserve the same remaining amount twice; repeated validator calls do not consume twice; settle/retry after process restart is idempotent; total spend does not reset at 100 summaries or include the wrong grant generation; both verification and repair respect the same intended total and their separate ceilings.
- Existing relevant suites: `check-authorization/tests/{contracts,redeem,repair,provider,reveal-holder}.test.ts`, `service/runtime-adaptation/tests/{result-check,repair-authority}.test.ts`, `flow-settings-requests/tests/stored-check-authorization.test.ts`, and `api/tests/flow-check-authorization.test.ts`. Add host-authority integration tests with real isolated stores and fake provider transport. No paid calls are needed to prove admission and custody.

Validation: read-only `rg`/`Get-Content` traced the named types, pure redemption functions, metadata guards, host resolver, key reveal and budget construction in paired t914 Core. No builds/tests/browser/cloud/provider calls or git operations ran.

Not verified: a legitimate durable standing grant service, concurrent billed spend enforcement, or live standing execution. They are concrete missing prerequisites, not verified guarantees of the current implementation.
