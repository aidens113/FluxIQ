## Established implementation

- `packages/sdk/src/keys/` already generates and loads Ed25519 PEM keys, derives IDs, resolves INI profiles and signs proofs. `session/create-session.ts` implements discovery, proof exchange, cached bearer sessions, renewal at 80% of lifetime, one clock-skew correction and invalidate-on-401 support. Its server tests use a fake engine, not a production implementation.
- Production `packages/fluxiq/src/server/headless/program-api-listener.ts` mounts program API, managed-client routes and FluxNode API only. No `/api/keys/session` route, public-key registry, nonce store or key-session store exists in the inspected platform/server trees.
- `server/fluxnode-api/api-handler.ts` runs `checkOpenModeGuards` for every request and passes constant `FLUXNODE_OPEN_MODE_CALLER` to every operation. There is no auth option. `FluxNodeCaller` in `framework/automation-service/service/fluxnode/fluxnode-service.ts` is literally `{ principal: "owner", policy: "FluxNodeRunner", via: "open_mode" }`. Runtime work must eventually replace this limitation; do not pretend a session endpoint alone enables hosted runs.
- Open guards currently require loopback source and Host, no Origin, Sec-Fetch-Site absent or `none`, FluxIQ-Client, JSON POST. Preserve these for every unkeyed local call. `start-headless-server.ts` binds both listeners to 127.0.0.1 and selects local gateway profile.
- Existing IAM supports user/service-identity principals, workspace FRNs, session-policy intersection and audited per-request decisions (`platform/iam/authorize`). No FluxNode action/policy registrations were found in catalog/contracts/predefined trees. K8 v1 says keys bind to users; do not introduce a second service identity scheme just because the IAM primitive exists.

## Freeze the existing SDK wire protocol

Use these exact SDK formats; move neutral protocol definitions to a contracts seam if shared code is introduced. Server must not import SDK implementation or its fake engine.

1. `GET /.well-known/fluxiq` returns at least `{ instance: { id: string } }`. SDK caches ID. Web has discovery builders under `apps/web/src/app/api/discovery`; headless currently has no well-known handler. A deployment profile/discovery worker may own those web files: coordinate before editing.
2. `POST /api/keys/session`, JSON, `FluxIQ-Client: sdk`, body `{ v:1, alg:"FLUXIQ1-ED25519", keyId,time,nonce,aud,purpose:"session",payload:"{}",sig,publicKey }`.
3. ID is **`fxk_` plus the first 26 base64url characters of SHA256(SPKI DER)** (`sdk/src/keys/key-id.ts`), not hex and not the entire digest.
4. Canonical UTF8 signed text: algorithm, purpose, audience, key ID, time, nonce, SHA256(payload) hex, joined by newline with no trailing newline. Refuse CR/LF in each field. Time is `YYYYMMDDTHHMMSSZ`; fresh nonce is 16 random bytes base64url; signatures and SPKI are base64url. Audience is configured origin + `#` + stable instance ID, never attacker-supplied Host/forwarded origin.
5. Success `{ sessionToken,expiresAt,serverTime }` (times epoch ms or ISO accepted by SDK). Fake returns extra principal/policy, not required by SDK. Subsequent requests use Authorization Bearer. Existing session test expects `fxs1.` token prefix; preserve compatibility unless intentionally updating contract/tests together.
6. Error `{ error:{code,message,serverTime?} }`. Fake codes are `key.bad_proof`, `key.unknown`, `key.bad_audience`, `key.clock_skew`, `key.bad_signature`, `key.replayed`. Unknown keys are 401. SDK retries `key.clock_skew` once using returned server time. SDK implicitly discovered keys downgrade to unkeyed on session-endpoint 404; **this must never become remote/service-mode authorization**. Server service mode must always reject unkeyed requests independently of client behavior.

## Security and persistence requirements

- Public key in proof is not enrollment. Resolve a previously enrolled active record, recompute key ID from trusted SPKI, compare any supplied SPKI, verify Ed25519 only, exact purpose/audience/payload, strict finite valid time, +/-300 seconds, canonical base64url and nonce entropy/length. Fake verifier is reference protocol, not a hardened implementation: do not copy it as production security.
- Durable records: key ID/public SPKI/user ID/workspace ID/creation/revocation/last-use, bounded session expiration and token digest (never raw bearer), key-session linkage; session auth rechecks key and account enabled state and membership. Session policy restricts IAM, never elevates the bound user. Defaults 1 hour, allowed range 15 min to 12 h per K8.
- Nonce consumption must be atomic across concurrent requests and service processes, retained 600 seconds; restart cannot reopen the proof window. Existing generic `PlatformRecordRepository` is list/get/put/delete with **no compare-and-set or transaction port**. Its last-writer-wins wrapper plus an in-process queue cannot prove cross-process replay protection. Add a dedicated transactional key repository/SQLite seam or extend a real atomic persistence capability; do not claim generic get-then-put meets this requirement.
- `platform/store/types.ts` explicitly excludes key/session material from account records. Put authentication persistence in a focused `platform/keys/` ownership tree, not account records or automation internals. Reuse repository infrastructure where sufficient, not the account entity shape. No private key may reach or be stored server-side. Project `.fluxiq` may reference a profile, never hold private PEM; client keys live under home `.fluxiq/keys`.
- Stable configured audience/instance identity must survive restart. Key management needs authenticated enrollment/list/revoke authorization; device login, extension migration/host launch tickets, browser deterministic custody and one-time link flows are separate later units, not acceptance claims for initial exchange.

## Commerce seams: future billing separate from authentication

- `platform/panel/types.ts`: `PlatformBillingProvider` is only `{id}`; `PlatformEntitlementPolicy` is `{id, allows(accountId,entitlement)}` with documented absent=>allow. Registry registers at most one each. These are extension points, not billing implementation.
- `platform/store` has accounts/workspaces/memberships/link tokens/idempotency only. `PlatformRecords` wraps a structural repository at platform scope, ID prefix `kind/key`; `createPlatformStore` chooses memory without repository. No customer, subscription, checkout, webhook, price, payment or entitlement-grant records found.
- `platform/provisioning/context/types.ts` accepts static `entitlements.organisation`; `create-provisioning-context.ts` defaults false. It is not connected to the registered entitlement policy. Existing hooks account.created/disabled/deleted/workspace.created offer lifecycle integration, but failures are isolated, so they cannot serve as authoritative synchronous billing admission.
- Actual web composition owner is `apps/web/src/server/provisioning-listener/platform-services.ts`: SQLite platform.store/platform.iam plus identity and audit, currently tenancy single. Tenancy worker owns forthcoming composition changes: commerce/key workers must not concurrently change it.
- Bounded next commerce unit: new `platform/commerce/{model,storage,runtime}/**`, immutable provider event IDs and atomic idempotent ledger/application, account/customer mapping, subscription/entitlement state and a provider-neutral resolver. Real persisted restart/duplicate/out-of-order event tests first. Provider secrets/signature verification/raw-body webhook/checkout return URLs belong a later explicitly wired provider adapter + thin server routes; never fabricate paid success. Extend panel billing port only once its operations are concrete.
- Service admission must fail closed when commerce policy or required subscription state is missing; preserve explicitly local/self-hosted independence via deployment-mode resolution, not a global change making every absent policy deny. Billing eligibility follows authenticated account/workspace authorization; it never authenticates callers or bypasses IAM. Do not mix subscription tokens with the existing Ed25519 credential system.
