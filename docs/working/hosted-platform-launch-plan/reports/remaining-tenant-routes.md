Outcome: Done, discovery only. Only this report changed. Source/tests, shared working state, package files, builds/dist, private/runtime state and git were untouched; no server/browser/provider calls or test consumers ran while the lead replaced shared outputs.

**Recommendation:** implement a dedicated held stream owner plus the run-dataset route, and a workspace-scoped presentation owner plus gateway snapshot/context. Parallel buffered client-route and account-read migrations can use the existing adapter. Separate credential-only teardown and account-wide member mutations from content routing; changing their authorizer alone would be incomplete.

## Stream owner contract

Add a narrow owner for a selected `WorkspaceRouteContext` plus a typed async byte/string producer and explicit response metadata. Do not pass streams/arbitrary Response through `withWorkspaceRouteJson`, and do not release in the dataset route's ordinary return/finally when returning a lazy body.

1. Select/authenticate once, freeze route resources/domain/format, hold the lease, and revalidate before/after awaited domain and export-descriptor reads. All refusal/setup/response-construction paths release it. Before headers, preserve safe 401/403/503 and domain-hidden 404 responses.
2. Transfer ownership to one body lifecycle before returning Response. Each pull has at most one underlying `next()` in flight and follows demand/backpressure. Revalidate before the read and again after the awaited read, immediately before any outward enqueue or EOF publication. Never reacquire or switch tenant midstream.
3. EOF, consumer cancel, request abort, lost authority and producer failure share one idempotent terminal/cleanup promise. Mark terminal before asynchronous cleanup, detach abort listeners, suppress late chunks from an outstanding read, settle/return the producer once, then release the selected lease exactly once. Producer rejection/cleanup rejection produces fixed feedback without raw store paths/data.
4. An async generator's `return()` may wait behind a pending `next()`. Keep the outer lease until producer work settles; do not pretend cancellation undoes an in-flight read or release the tenant while it can still be used. If later evidence requires cooperative abort for a nonsettling storage read, give that capability to the actual producer; do not invent a timeout or a second tenant-selection mechanism.
5. After headers/chunks have gone out, an auth failure terminates the body; it cannot retroactively replace HTTP status or retract bytes. No JSON error records injected into CSV/JSON exports. Existing Core generator owns dataset-store/audit cleanup (`framework/automation-service/service/datasets/run-datasets.ts:359,377`); the web stream owner owns the **separate tenant-instance lease**. Preserve export limits/encoding and once-only producer cleanup.

## Presentation/context owner

The genuine owner is the web workspace presentation layer, not generic gateway authentication or the process-global primary:

- `lib/fluxiq.ts:50,133,165` holds one `automationStudioContexts` map. Its keys encode only user and optional client (`lib/automation-studio-context.ts:85`); the same human across two workspaces shares that namespace. Presenter lookup omits the paired client's id and reads the wildcard user context (`fluxiq.ts:137`), ignoring an existing client-specific selection.
- Presenter computes readiness from `primaryOf(state)`, exposes global `contextCount`, and includes `hostModulePath` even on service (`fluxiq.ts:135,145,155`); the service-only omission covers hostRoot/fluxiqDir, not that path. Treat these as source-level sensitive/global payload findings, not a verified network disclosure.
- Recording-context provider is installed only on primary (`fluxiq.ts:279`), reading that same global map. A tenant presenter migration must bind a provider to each actual tenant instance; simply adding workspace to an HTTP key leaves recording context inconsistent.

Introduce one collaborator with explicit server-owned `{workspaceId, userId, clientId?}` inputs, selected instance, and scoped context storage. Public presentation uses an explicit service-safe allowlist and selected-instance readiness. Context is a project-selection hint, not permission: tenant/domain/project/Flow authority still runs at use. Body clientId cannot select a workspace/owner or grant access to another client. Preserve intentional own-user wildcard/client-specific behavior **within** a workspace. Define delete/reload/eviction behavior and ensure late results cannot restore removed context. Root should wire primary/tenant creation and recording callbacks through this collaborator; keep `lib/fluxiq.ts` a thin composition owner. The existing five-minute context freshness is selection liveness, never a credential/key lock or lease-lifetime substitute.

Gateway snapshot additionally needs an honest caller view: whole-workspace admin visibility and own-user/client visibility require explicit policy, so pending pairing references, foreign browser state and audit cannot be handed to an ordinary paired caller merely because selection now names the right tenant. Reuse service views where genuinely suitable; the existing generic paired response projector does not provide a gateway snapshot filter (`server/program-route/program-route.ts:542`).

## Teardown and member mutation boundaries

**Forget:** content routing requires an active eligible identity and exact current session. Credential-only teardown must still end its own trust after logout/disablement or loss of the socket. Existing `server/connect/revoke.ts:5` already resolves authoritative proof, excludes managed/primary hosted records, verifies workspace existence and holds the target lease; invalid/inactive proof is a processed no-op and persistence failure can throw. Reuse/extend a teardown-only port without exposing a context/caller for reads or writes. Preserve legacy `{forgotten}` and local/self-hosted semantics deliberately; do not silently translate void success into a true persistence claim. Make IAM classification reflect this restricted proof-only operation, without adding broad public exemptions.

**Member lifecycle:** `change-member.ts:90` scopes `setPolicies` by workspace, but `:91,92` calls global `disableAccount`/`enableAccount` with no workspace id. `revoke-invite.ts:34` also disables/deletes/restores an entire account. A target's membership in the selected workspace does not by itself grant its administrator ownership of that person's global identity or other memberships. Migrating only the authorizer could newly confer that power. Account reads can move first through a dedicated read context, leaving existing mutation dependency builders unchanged. Member mutation needs a separate authoritative workspace-membership lifecycle design/implementation or genuine host authority; preserve current service operator denial and multi `remove` refusal instead of widening access. Retain existing self/owner protection, credential reproof, invite race handling and server-side role allowlists. Committed provisioning changes cannot be undone by a later HTTP authorization refusal.
