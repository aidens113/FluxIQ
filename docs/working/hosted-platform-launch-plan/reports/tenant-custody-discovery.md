# Tenant identity and credential custody discovery

Outcome: Done (source review only; no runtime acceptance claimed).

## Concrete finding

Hosted account identity is primary-owned, while every tenant owns separate Secret Keys records, credential wraps and in-memory custody. Current program routing correctly authenticates the primary session, but tenant key handlers, holder vouch and revocation wiring still ask their tenant's distinct Identity Access. These are separate incomplete seams; copying primary users, session unlocks or model keys into tenant stores would hide the mismatch and break ownership.

A strict hosted credential grant must persist a **locked, zero-box, tenant-local holder linked to the approving primary session digest**. Connection does not require a configured or unlocked model key. The existing first-unlock proof remains what permits key access.

## Strict grant contract

Keep the proposed server-owned `grantCredential({ credential, trustedClientId, userId, approvingSessionDigest, expiresAt }): Promise<void>`. Bind its implementation to exactly one trusted workspace/tenant at composition; neither user payload nor a lookup hint chooses the workspace.

1. The hosted authority validates the approving digest against primary identity: matching live session, matching user, enabled user, active membership and existing selected workspace. An existing public `snapshot` can prove this in the current single-process deployment. A focused public `validateSessionDigest`/equivalent port would avoid a snapshot scan; passing the digest to `validateSession` is incorrect because it hashes its input.
2. Call an awaited **strict** enrolment operation on the selected tenant's `credentialUnlocks`, mapping expiry to `expiresAtMs`, holder to `secretKeyPairedHolderId(trustedClientId)`, and the supplied digest directly to `approvingSessionDigest`.
3. Enrol a fresh locked holder with `boxes: {}` even if the person has zero keys. Do not call `unlockedSessionFor`, `HeldKeys.liveUnlocksFor`, primary key stores, or another session's reveal authorization. Zero unlocked keys is a valid connection outcome.
4. Reject mismatched existing owner/approval binding. Make any replay explicitly idempotent for the same binding; do not overwrite another owner or silently replace its approving session. A fresh trusted-client id should normally have no existing holder.
5. Let validation/persistence failure reject the issuer. Do not call the guarded gateway custodian as the mandatory authority. Token publication must follow successful trust persistence **and** strict grant persistence. On a failed grant, remove/revoke that new trust and drop any provisional holder; a racing signout/revoke before publication must still prevent returning the credential.
6. The strict enrolment operation needs rollback/serialization for its own provisional memory, just as authoritative trust does. Existing `presentCredential` mutates `records`/HeldKeys before its awaited write, and convenience `persist` may be absent in local/in-memory instances. A hosted mandatory port must not treat absent persistence as successful durable grant.

Existing `CredentialUnlocks.presentCredential(holder, credential, { verified: true })` is a useful implementation building block: direct persistence errors propagate and its new-record path starts locked. It is **not** already the full strict contract: it does not validate the primary session/workspace, can early-return from held state, preserves an old approval link on an opened existing record, and does not restore provisional memory on a failed write.

Specific integration trap: current `ClientGatewayCredentialCustody.issued` accepts `approvedBySessionDigest`, but `secretKeysCredentialCustody().issued` still destructures only `approvedBySessionId` and hashes that. A digest-only hosted issuer therefore loses the approval link through that hook today. Prefer the explicit strict port; also preserve direct-digest handling deliberately in the optional lifecycle observer. If both raw and digest forms are supplied, prove they agree; never hash an already supplied digest.

## Smallest coherent ownership changes

1. **Inject trusted identity authority, keep key storage local.** Add an optional runtime authority port for hosted tenant construction. The tenant key API requires structural access to primary `validateSession`, `snapshot`, `authorizeSessionCredentials`, and `authorizeSessionPasswordPin` (narrow the handler types instead of forging an `IdentityAccessService` cast). Use that same authority for panel holder vouch and registry identity gates where needed. Default/unset retains local/self-hosted behavior. The tenant gateway remains the paired-holder vouch owner, with current hosted owner/membership checks applied by the host.
2. **Unlock the selected tenant from the person's actual proof.** Under service login, authenticate only at primary, resolve the workspace from trusted membership, hold its lease, and use the submitted password plus the *same* primary session to unlock that tenant's own records. No primary key material is copied. The no-key case succeeds with count zero. A workspace first visited later needs its own explicit password proof or an existing cookie-wrapped unlock; presentation alone cannot invent one. Local login remains unchanged.
3. **Keep the exact-session key proof.** Tenant Settings should continue requiring payload `authSessionId === request.actor.sessionId` and matching primary user. The primary authority verifies password/TOTP; tenant `unlockSession` opens only local records. First paired-client unlock uses the existing same-user `liftable`/first-unlock ticket gate and an explicit selected holder, as the current pairing route does when given a password. Ordinary connection consent must not inherit key-management password/PIN gates.
4. **Use one primary-owned custody event coordinator.** Public `subscribeSessionRevocation` exists but announces raw ids only. Digest session-end subscribers and credential-change phase subscribers are currently constructor-only. Add supported public subscription/source ports with unsubscribe, or construct a host-owned relay when primary is built. A tenant must not create local sessions/users just to receive these events.
5. **Cover cold persistence, not just open instances.** An open-instance callback misses durable tenant wraps after eviction. Keeping the old callback after eviction retains stale services over roots that may have reopened. The coordinator must invoke the current workspace mutation owner under manager leases, include previously affected/cold workspaces, and retain durable session/credential-event replay with a watermark/barrier before a reopened tenant can release keys. `PlatformStore.listWorkspaces()` exists; current membership alone is insufficient after removal. A synchronous fanout alone still needs durable failure/restart handling: current Identity session-end listeners report failures *after the session is revoked*, so an unwritten tenant lock cannot be assumed to replay.
6. **Respect password phase semantics.** The current local credential-change subscriber prepares tenant seals using the old password, commits after identity writes, and aborts on refusal. A primary password change/reset must reach each affected tenant through those phases; merely passing primary auth to key Settings does not re-seal tenant records. An administrator reset with no old password must lock old wraps, not copy or pretend to decrypt them.

The durable event barrier is a prerequisite to claiming hosted signout/restart custody correctness. Do not replace it with “approving session must always be live”: the current contract lets a paired client outlive ordinary panel-session expiry, and an explicit later unlock can reopen a holder whose original approving session ended. Both need event ordering, not a permanent liveness test on the original digest.

## Required narrow tests

- Real primary identity plus two separate tenant stores/custodies: ordinary service login opens only the selected tenant's own records; zero-key login and zero-key strict browser issuance succeed.
- Real tenant key create/unlock/rotate requests through the primary-authenticated program route: correct actor/session works with empty tenant identity; a mismatched payload/actor session, another user, or another workspace cannot lend its held unlock to the grant. Explicit same-user password proof naming an eligible holder remains supported.
- Strict issuance persists the exact primary digest and no raw cookie/credential, starts with no boxes, never borrows an unlocked session, and fails without returning a token when authority or mandatory persistence rejects. Include signout/account disable/member removal while grant persistence is held.
- Restart restores only previously proved tenant boxes from the correct credential; a new unproved client stays locked. Evict/reopen retains only that workspace's HeldKeys and disposes event subscriptions without leaving stale writers.
- Signout removes its own panel unlock and locks exactly its approved paired holders; an unrelated still-live approval remains usable. Signing in elsewhere does not lift the lock. Explicit same-user proof naming that holder can re-unlock it. Whole-user revocation/reset locks all that user's holders, including tenants cold during the event, without touching another user or workspace. Reopen after failed lock/crash must replay before key release.
- Password change from its exact actor keeps only the allowed actor/approved holder, re-seals each affected tenant's own records, locks other sessions/holders, and survives a restart; administrator reset does not claim old sealed data is decryptable.

Existing useful suites to extend: `programs/_shared/tests/runtime-credential-unlock.test.ts`, `programs/secret-keys/runtime/unlocks/tests/{credential-unlocks,credential-unlock-proofs}.test.ts`, `programs/secret-keys/api/tests/unlock-cross-user.test.ts`, `programs/identity-access/runtime/sessions/tests/session-revocations.test.ts`, web login/logout tests, workspace manager eviction tests, and `server/program-route/tests/identity-authority.test.ts`. Existing runtime custody tests use one identity/key/gateway runtime; they do not prove primary/tenant separation.
