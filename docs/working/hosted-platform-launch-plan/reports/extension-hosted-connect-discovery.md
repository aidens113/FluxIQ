# Hosted extension connection: next implementation unit

Outcome: Done (source-only discovery). No source, other report/shared document, build/dist, browser, account, runtime/private storage, server, provider or git mutation was performed. Roots below are the paired t914 Core and extension checkouts.

**Recommendation:** implement the extension's server-bound credential repository and authentication-tab policy first, then the existing fixed-client PKCE flow and its connection composition. Freeze the two discovery decisions below before activating hosted dialing. Do not introduce a second credential scheme, managed-host ticket, tokenless hosted hello or model-key unlock.

Token/revoke require `fluxiq-client: browser-extension` and `Content-Type: application/json`, with an 8 KiB streamed body bound. Missing Origin is admitted with that header; a present Origin must equal publicOrigin or be an admitted configured extension Origin. Chrome/Edge ids require separate exact `chrome-extension://<id>` entries. Firefox allows exact `moz-extension://<uuid>` or the controlled `moz-extension://*` rule; no arbitrary web wildcard. Send from the privileged background using host permission, `credentials:"omit"`, `redirect:"error"`, `cache:"no-store"`, `referrerPolicy:"no-referrer"`. Never set/forge Origin or remove the required header to evade admission. Browser preflight behavior is unverified; routes expose POST, so any needed narrow OPTIONS support must be proven in later browser acceptance, not assumed.

Token errors: 400 `invalid_request`, `invalid_grant`, `unsupported_grant_type`, `email_unverified`, `client_limit_reached`, `account_disabled`; 401 `invalid_client`; 429 `rate_limited`; 503 `temporarily_unavailable`. Admission can instead refuse 403, 404 outside service, 413 or 415. Parse existing success/error schemas, but map codes to fixed local UI text; untrusted error descriptions/exception messages must not echo a verifier, code, credential or authorize URL.

## Core decisions/dependencies to freeze

1. **Instance identity.** Current discovery builder emits id only from optional `FLUXIQ_INSTANCE_ID`; neither service settings nor the schema guarantees it exists. Hosted credential use needs a stable nonempty instance id pinned with canonical origin and gateway. Recommend requiring the existing field for extension-hosted admission and ensuring service composition supplies a stable unique id. Missing/changed id must prevent credential reuse and trigger explicit reauthentication/configuration feedback; never substitute instance name, build digest or a guessed id. This is a bounded Core discovery/configuration dependency, not a new token endpoint.
2. **Local reference pairing capability.** Current `referenceCode:false` is the unimplemented typed Flow B (eight characters/ten minutes). It is not the existing gateway `pairingReferenceCode` produced by tokenless local hello. Preserve that known protocol only behind an explicit local/self-hosted selection plus an authoritative capability; recommend a separately named additive legacy-gateway-pairing flag rather than advertising Flow B as implemented. Until the lead freezes its representation, missing/false hosted flags never authorize service fallback. `/connect` currently only explains how to start; it cannot accept a typed code.
3. **Persistence failure seam.** Core `client-gateway-websocket/src/transport.ts` awaits tokenStorage.write before acknowledgement/session_ready, which is correct. Its message listener currently invokes the async handler with `void` and no rejection catch; a failed write has no explicit terminal storage-error transition. Existing extension `persistSession` adopts in memory before save. New adapter must publish only after durable commit and close/stop authentication use on failure. Recommend a bounded Core catch/closed error signal for failed credential persistence, preserving the existing acknowledgement/rotation order; do not fork the generic transport downstream. Add a regression proving no ack, no ready callback and no unhandled secret-bearing rejection on write failure.

No missing PKCE authorize/token/revoke endpoint was identified. Fixed extension authorization remains separate from future registered third-party applications. Server signing/tenant routing establishes credential authority; the client treats the credential as opaque and independently binds its storage/use destinations.

## Proposed typed seams

Keep secret-bearing types/repositories background-private. One named export owner per file, barrels per directory:

```ts
type ServerBinding = {
  origin: string; instanceId: string; gatewayUrl: string;
  authorizeUrl: string; tokenUrl: string; revokeUrl: string;
};
type BoundCredential = {
  binding: ServerBinding; installId: string; connectedClientId: string;
  userId: string; workspaceId: string; expiresAt: number;
  credential: string; revision: number;
};
type AuthAttempt = {
  attemptId: string; binding: ServerBinding; installId: string;
  tabId: number; state: string; verifier: string;
  phase: "waiting_redirect"; selectionRevision: number;
}; // exchanging journal drops verifier/state; no persistent raw code
```

`CredentialRepository` reads only an exact binding and commits/replaces/revokes with expected revision. `HostedConnect.start/cancel/restore` returns safe attempt/status data only. `ActiveCredentialAuthority` supplies a bound HTTP lease and the existing gateway token-storage port; addresses cannot come independently from mutable settings. `AuthenticationTabs` exposes an eligibility predicate and an awaited restoration barrier, not codes/verifiers. Local legacy binding is a separately tagged mode; it cannot be interpreted as a hosted instance without evidence.

Use an extension-origin IndexedDB repository for durable credentials and pending revocations; pending PKCE state belongs in privileged browser-session storage, never local/sync, page storage or URLs beyond the standard authorize state/challenge. The earlier `extension-connect-discovery.md` storage evidence remains relevant: optional unawaited local.setAccessLevel is not a cross-browser isolation guarantee. Retain no memory-only/different-lifetime fallback for lasting credentials. Provider-free browser acceptance must prove actual content-script isolation; mocked API availability cannot establish it. No new identity/cookies/unlimitedStorage permission is justified; existing manifests already have tabs/storage/webNavigation and broad automation host permission. Check/request only selected Core-origin access from a real own-panel gesture if withheld; do not assume that gesture survives asynchronous discovery/background messages. New start/cancel messages remain control-page-only, with origin/attempt id inputs and no caller-supplied code or credential.

Critical integration details:

- `extensionHello` currently spreads session.token. Remove that duplicate authority for the new path: a checked tokenStorage.read cannot protect against transport preferring an old explicit hello.token. `coreApiCredentials()` currently combines mutable HTTP URL/global token, while tokenStorage.read ignores saved serverUrl. Every HTTP consumer (programs, project lookup, assets/traces, recordings, revoke) must receive one pinned credential destination, reject credentialed redirects and ignore late replies from replaced connection generations.
- Start with an inactive blank/non-recordable owned tab; register its returned id durably before navigating/activating the authorize URL. Register browser listeners synchronously and route them through the hydration/serialization barrier. Popup closure and worker restart cannot own or cancel the attempt implicitly.
- Completion is valid only for the saved tab, exact origin, exact `/connect/done`, empty search, valid fragment and exact state. Persist an `exchanging` claim before POST and delete transient secrets before reporting completion. Concurrent URL events cannot both claim. Do not hold the mutation queue across network I/O: cancellation/profile changes must progress, and finalization rechecks selection revision.
- Cancel/deny/tab close/server change invalidate the attempt. Abort does not prove the server did not mint a credential. Revoke a known delivered but unadopted credential against its original pinned server; retain a private pending revocation when possible. Lost response/worker death in exchanging requires fresh consent, never code resubmission. A completely failed store plus lost response cannot guarantee cleanup; report uncertainty and allow fresh same-install consent, whose existing issuer replaces prior trust in its binding.
- Browser restart loses transient PKCE secrets, so unfinished consent cannot resume as an exchange. Never adopt a restored done fragment or identify an owned tab by state alone. Tab ids are not a durable cross-browser-start identity guarantee: rehydrate within the browser session; after a new session invalidate old ownership ids and keep known auth/return/signup routes outside automation. A restored arbitrary external auth destination cannot be declared safely owned from source alone; later browser proof must establish its recovery policy, without blanket exclusion of unrelated sites or closing guessed tabs.
- A fresh PKCE credential has a token before its first hello. Core's lineage rule would otherwise treat it as a resume and reuse the global `fluxiq.outbox`. Give each newly trusted binding a fresh scoped outbox/lineage and reset old session/project/recording authority; preserve existing loss accounting instead of replaying one owner's messages under another. Normal reconnect/rotation retains that binding's lineage.
- Handle current 0.2 `server.revoked` by deleting only that bound credential, stopping its reconnect and offering real sign-in; `server.going_away` retains it and honors retryAfterMs. Current extension handler does not process those notices. Do not map generic transport errors, provider setup failures or server drain into revocation. Successful authentication introduces no key-unlock step.
