# Authentication-tab privacy composition discovery

Outcome: Done (read-only discovery and implementation plan). Only this report was written. No product source, tests, package files, shared documents, build/dist, browser/profile, server, provider or git state was changed. Paths prefixed `extension/` below mean downstream `apps/extension/src/`; Core paths are explicit.

The existing registry is a sound ownership foundation but remains unwired. Filtering a tab list alone will leave direct state updates, chat context, content-script startup, explicit commands and visual capture open. Compose one background privacy authority over that registry, with admission before acquisition and generation checks before publication. Prefer investigating the standard native identity flow as the hosted-auth surface before choosing broad restore quarantine as the normal experience. Current Chromium has an explicit restore exclusion for that surface; it does not provide tab/capture isolation, and the inspected Firefox implementation does not establish the same restoration guarantee.

## Existing foundation and required boundary

`extension/background/authentication-tabs/index.ts` exports `AuthenticationTabs`, its session store, route policy, errors and narrow types. The current public contract is `new AuthenticationTabs({store,routes})`, `ready()`, `status()`, `eligible({tabId,url?})`, `own(tabId,attemptId)` and exact-attempt `release(tabId,attemptId)`.

Claiming reserves exclusion synchronously, then persists ownership before resolving. Ownership wins at every URL, including blank tabs and off-origin signup. Loading or failed storage denies admission. Same-session hydration restores owners; a different session marker drops old numeric IDs. Routes compare canonical origin and decoded path with explicit descendant boundaries; query/fragment never confer trust. Privileged `storage.session` has no local/memory ownership fallback. The foundation report records 60 passing tests; those tests were not rerun here.

One composition authority must own all registry mutation, route changes and privacy generation. Consumers receive a read-only port, never the writer or another ownership map. Keep normal scheme restrictions separate from exact authentication exclusion. Ordinary pages on a Core origin are not automatically private auth pages. Configure the exact connect/authorize/return, relevant login and configured signup routes from trusted profiles; do not infer trust from an arbitrary request URL or redirect parameter. Retain old profile auth ownership/routes during a profile switch.

There is an acquisition boundary before those background consumers. Both manifests declaratively inject `content/index.js` and `page-world/index.js` at `document_start` in all matched frames. `content/index.ts` immediately calls `recorder.sendReady()`, whose `basePayload` reads `location.href` and `document.title` even when recording is off. `setRecordingState(false)` flushes a pending input before disabling. Default recorder inactivity therefore does not establish auth-page privacy.

`page-world/index.ts` installs probes immediately. In particular, `page-world/dialog-override.ts` records unarmed dialog messages/responses, including prompt text, in a DOM attribute; `page-world/request-starts.ts` retains fetch URLs for request tracking. These are current source findings, not proof that data has reached a server. A background drop cannot undo these reads. The next content lane must make data collection inert until admission, use a data-free readiness handshake, and add privacy suspension that drops pending input/mutation work without flushing. Preserve early wrapper installation only where required for ordinary automation, with pass-through behavior and no observation while inactive. Audit the other probes invoked by that same entry for equivalent eager collection. MAIN world remains page-controlled: no private ownership records, secrets or trusted authorization decision belong there, and forged DOM probe signals must never bypass isolated/background admission.

`background/action-evidence.ts` itself sends only command-boundary metadata to the test observer, not page bytes. Keep the command privacy check before that hook; the external observer can trigger evidence capture. It is not a substitute for the production capture gate.

## Proposed narrow public ports

These are proposed next-unit interfaces, not implemented/exported APIs. Place read-only browser-neutral-to-background types in `extension/shared/tab-access/` and the adapter under the existing `background/authentication-tabs/` owner. Runtime modules receive the port through their existing dependency objects and do not import the background singleton.

```ts
type TabAccessLease = Readonly<{ tabId: number }> & OpaqueAdapterLease;
type TabAccessDecision =
  | { kind: "admitted"; tab: Readonly<BrowserTabSummary>; lease: TabAccessLease }
  | { kind: "excluded" | "unavailable" };
type AutomationTabAccess = {
  project(tab: Readonly<BrowserTabCandidate>): TabAccessDecision;
  inspect(tabId: number): Promise<TabAccessDecision>;
  revalidate(lease: TabAccessLease): Promise<boolean>;
  current(lease: TabAccessLease): boolean;
};
type ChatPageLocation =
  | { kind: "admitted"; url: string; lease: TabAccessLease }
  | { kind: "absent" | "excluded" | "unavailable" };
```

`BrowserTabCandidate` contains only the private browser-supplied fields needed for classification, including ID, committed URL and pending URL. `BrowserTabSummary` is the existing admitted projection, not an unfiltered `chrome.tabs.Tab`. Leases are opaque local objects issued by the adapter, never accepted from wire payloads or persisted. Their private state binds global privacy generation, tab/document generation and active owner generation. `revalidate` obtains current private browser metadata and checks every binding; `current` is the final synchronous check after the last await. Consumers may not switch tab, owner or credential destination after acquiring a lease. A claim followed by release must still invalidate a result that began before the claim.

The existing registry needs small additive observations rather than a second map: an ID-only `ownership(tabId): "unowned" | "excluded" | "unavailable"` for pre-read refusal, `captureBlocked(): boolean` covering owners/reservations/loading/failure, and an atomic `updateRoutes(routes): void` for trusted profile changes. The adapter advances its generation before these lifecycle changes. Keep `eligible` as the final registry route/owner decision; the general scheme check and any restore quarantine further restrict it. No caller can use an invented URL to ask whether an ID is owned.

Only privileged lifecycle composition receives `own/release`, trusted route update and controlled creation. Content receives a nonsecret, document-bound admission response to an initial message containing no URL, title, snapshot or element data. The background binds it from sender tab/frame/document evidence, not caller fields. Keep content inactive if admission cannot be obtained; invalidate old grants on navigation, privacy suspension, worker loss or owner change. Before navigating an already live tab into auth, suspend its content capture and clear pending state before releasing the navigation. Background intake still revalidates every result; content-side gating does not replace that authority.

## Visible capture and lifecycle ordering

Chrome and Firefox document `captureVisibleTab` as capturing the active tab in the selected window, not a requested tab ID. Its API has no atomic target-tab capture option. Thus prechecking `tabs.get(requestedId)` or active-tab equality does not close the race. [Chrome tabs capture](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-captureVisibleTab), [Mozilla captureVisibleTab](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabs/captureVisibleTab).

For a tab-based auth surface: synchronously enter the privacy generation and block new visible captures; persist a private nonsecret restoration-risk latch; create an inactive blank tab; claim it durably; suspend any existing content collection; wait for already-started visible browser captures to settle; only then navigate/activate auth. Suppress visible screenshots while any auth owner/reservation or unresolved restoration risk exists. Existing admitted ordinary DOM/recording operations may continue without screenshots. Do not change authenticated gateway/model-key readiness. A missing visual sample must be reported honestly as privacy unavailable, not fabricated or represented as a key unlock.

Every in-flight capture also rechecks generation before serialization, hashing, caching, persistence, upload and forwarding. Discard protects those later boundaries; it does **not** undo privileged browser-memory acquisition. Generation checks alone are insufficient if auth is allowed to appear while an older capture is still executing. Known route changes and unproved restores must invalidate pending outputs immediately. Ordinary user-driven browser navigation cannot be made atomic by an extension-side precheck; later browser acceptance must establish the actual protected boundary rather than claim stronger browser API guarantees.

## Native identity surface: evidence, compatibility and recommendation

Investigated at the lead's request before selecting quarantine as product default. `identity.launchWebAuthFlow` uses a browser-managed interactive authorization UI and returns the final redirect URL to privileged extension code. Chrome generates `https://<extension-id>.chromiumapp.org/...`; Firefox derives its redirect host from the add-on ID. It needs the `identity` permission. Current manifests have neither that permission nor native-flow composition; Firefox already has a stable configured add-on ID. Local reference pairing need not call this API. [Chrome identity](https://developer.chrome.com/docs/extensions/reference/api/identity), [Mozilla identity setup](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/identity), [Mozilla getRedirectURL](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/identity/getRedirectURL).

| --- | --- |

Its destructor closes the popup. This is materially better than an ordinary `tabs.create` auth tab for restore, but it is not a tab-free isolated surface. The source is current upstream, not validation of the extension's supported Chrome/Edge builds. **Recommendation:** make a bounded native-identity browser proof the next surface decision, alongside the reusable admission work. Do not ship a permanent all-existing-tabs restriction merely because the user once signed in. A proven native surface can keep the restoration-risk latch scoped to a pending/uncertain attempt and clear it after verified terminal cleanup. Chrome source makes this a credible improvement. It does not remove the central gates, visible-capture suppression or inert content requirement: the visible native UI uses browser tab contents, and the API does not give an ownership ID before navigation. During native launch, treat unproved newly appearing tabs/windows as private until the surface can be correlated under the trusted lifecycle; no arbitrary `onCreated` event is sufficient. Propagate private ownership to auth-opened child surfaces. Do not begin reads while waiting to identify the native surface.

On local Cancel, invalidate the PKCE attempt immediately and refuse any later code/result. Do not claim an unavailable native abort call closed the UI; retain privacy restrictions until the UI actually terminates or recovery proves safety. Forced extension reload, browser crash/restart, moved tabs and child signup windows are explicit acceptance gates. If native behavior cannot be proven on a supported browser, restrict only the unproved tab capabilities through the fallback below or keep hosted start unavailable there with precise feedback. This is independent of an already authorized client's key access.

### Exact Core contract delta for a native option

No source changes were made. `getRedirectURL("connect/done")` preserves the existing path and fragment parser. The current syntactic path check in Core `packages/contracts/src/platform/connect/fields.ts` would need its documented semantics expanded to admit an explicitly registered native callback; the actual hard refusals are the same-origin equality in `apps/web/src/features/connect/model/authorize-request.ts` and `packages/fluxiq/src/platform/connect/runtime/create-service.ts`.

1. Add an immutable host-configured exact redirect allowlist for the fixed browser-extension OAuth client, defaulting to the current instance-origin `/connect/done`. Explicitly add each published Chrome/Edge callback and the stable Firefox add-on-derived callback. No wildcard native hosts, arbitrary request-supplied redirects, subdomain suffix trust or generic open redirect. Do not depend on Chrome's nonpublic alternate-redirect preference or Firefox's separate loopback exception.
2. Make web request parsing and Core authorize/exchange use that same trusted policy. Save the **requested allowed redirect** in the existing code record and return it in authorization; consume must match that exact saved value and the current allowed policy. Keep the existing verifier, install ID, user/workspace, approving-session, one-use/expiry and strict credential enrollment checks. Storage already records/compares redirect strings; its security invariants need no second grant scheme.
3. Advertise native callback support additively in discovery, with a distinct capability or exact redirect list frozen by the lead. Existing `authorizationCodePkce:true` does not prove that alternate callbacks are admitted. Old clients retain the existing same-origin `/connect/done` flow; old servers must not receive a guessed native callback.
4. Consent can keep its existing 303 fragment construction. For native flow the browser intercepts the configured callback; Core's done page is not involved. Parse the returned URL only in the privileged background: exact generated origin/path, empty query, current attempt/state and the existing strict fragment schema. Never render/log/persist the raw callback or replay a code after uncertain exchange.
5. Add native `identity` permission/capability handling only for the chosen hosted surface; derive and pin the actual per-browser extension identity. Preserve the separate server install ID and opaque credential scheme. No cookies permission, cookie reads, key unlock or new login/session store is implied. Update the earlier discovery report's assumption that identity permission is unnecessary if this option is chosen.

## Restore barrier fallback and its cost

Chrome documents that `storage.session` clears on extension reload/update/disable as well as browser restart. Tab IDs are only session-unique. Therefore missing session ownership cannot distinguish a safe browser restart from an extension reload that leaves an external auth page open. A regular owned popup has no published non-restoration guarantee. [Chrome storage lifetime](https://developer.chrome.com/docs/extensions/reference/api/storage#storage-areas), [Chrome tab IDs](https://developer.chrome.com/docs/extensions/reference/api/tabs#type-Tab), [Chrome windows](https://developer.chrome.com/docs/extensions/reference/api/windows).

Use a durable private **nonsecret risk latch**, separate from the session ownership store, before any tab-based/native pending auth is exposed. It contains no URL, token, code, verifier or persistent tab identity. Preserve it through crashes and uncertain cleanup; a storage failure while enabling auth refuses launch. An explicitly established never-used local path keeps its existing scheme behavior without requiring `storage.session` or `identity`. Absent/corrupt evidence on a previously active/migrated hosted path is uncertainty, not proof of never-used local mode. Do not silently downgrade to memory ownership. A safe terminal native cleanup may clear its scoped risk; ordinary restorable tabs need a stronger recovery policy because closed tabs can return with new IDs.

When risk exists and ownership cannot be reestablished, quarantine **all unproved tabs** before events/projections/commands run. This includes existing tabs and every later restored/manual `onCreated` tab; do not enumerate once then whitelist later arrivals. Permit only IDs returned by a fresh, internally controlled ordinary automation-tab creation under the current privacy/owner generation. The factory creates blank, admits its own returned ID and validates the intended ordinary destination before navigation. Privileged auth creation is a separate operation and can never create a clean-tab proof. Do not copy a quarantined tab's URL/query/fragment to manufacture recovery. A tab selected by raw ID or by a person is not technically proven free of abandoned auth.

Old tabs remain open and private. Ordinary DOM/actions/recording in the fresh controlled context remain usable; existing authenticated transport/model use stays ready. Visible screenshots stay suppressed while unresolved auth could be active in another window. The clean proof is current-session evidence, not a permanent ID; after losing its trusted marker quarantine again. A delayed auto-restore cannot earn admission from time elapsed, URL shape, reload heuristics or ID reuse. No unrelated user work is closed.

This barrier is enforceable but substantially restricts normal tab reuse until genuine recovery. It is a fallback/recovery state, not the recommended permanent post-sign-in default. Firefox has a useful negative marker port: `sessions.setTabValue/getTabValue` can correlate a private marker through close/restore despite a changed ID. Write/verify only a nonsecret exclusion marker before auth, then restore it into the existing registry before admission. It is not PKCE proof or permission to resume exchange. Chrome's published sessions surface has no equivalent tab-value API. [Mozilla restored tab values](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sessions/getTabValue), [Mozilla setTabValue](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sessions/setTabValue), [Chrome sessions](https://developer.chrome.com/docs/extensions/reference/api/sessions).

Firefox documents private windows as excluded from ordinary session restore, but private-window availability and extension-reload survival are separate issues; a regular popup is not equivalent. Do not claim an incognito/private workaround is portable from that fact. Unknown restored external authentication remains a hosted-launch blocker for unrestricted all-tab operation until the selected surface/recovery policy is proven. [Firefox session recovery](https://support.mozilla.org/en-US/kb/restore-previous-session).

## Owner, workspace and lineage transition

Use the already implemented `HostedCredentialSnapshot.lineageKey` (`background/credentials/runtime/state.ts`) as the private storage namespace. It binds server context, install, user, workspace, connected client and trust lineage. `runtime/commit.ts` retains lineage for valid rotation, and creates a fresh one for `new-trust`. Do not key ownership on raw credential bytes, credential revision or a gateway socket/session ID.

Current connection composition still uses global `fluxiq.outbox`, host-lease key prefixes and shared runtime histories. `gateway-session.ts` supplies an explicit hello token and token storage from mutable session state; `connection.ts` combines mutable API settings with that session token and adopts a session before its write completes. These are composition seams for the existing credential foundation, not reasons to create another token scheme.

| Event | Required treatment |
| --- | --- |
| Same bound owner/lineage reconnect or ordinary token rotation | Retain project, recording, outbox, in-flight/lease state and automation context. Commit the credential durably before acknowledgement/activation. Credential bytes/revision changing is not an owner switch. |
| Server/instance/gateway, user, workspace, connected client or trust lineage change | Increment owner generation synchronously; stop admitting old commands/events/captures/sends; cancel attempts; stop the old recording against its pinned old endpoint; retire old socket/callbacks. Checkpoint old outbox/loss, then construct a fresh connection with the new lineage-scoped storage/HTTP authority. Publish only after durable credential selection. |
| Any scope switch | Clear old active URL/tab/context, projects and pending project adoption, recording IDs/log/steps/navigation/click evidence, extraction sessions, activity/overlay targets, screenshot/trace digest caches and pending capture outputs. Also reset runtime global automation tabs/history, document/readiness/look reuse/frame geometry and timers. Existing per-connection objects can be replaced to clear cohesive private caches; global runtime caches need explicit reset seams. |
| Switch while old async work waits | Every late reply/ack/session write carries the original owner/endpoint generation and is discarded when stale. It cannot adopt a project, enqueue/upload evidence, overwrite the new session or clear the new owner's credential. |
| Browser auth-tab ownership | Global privacy state outlives a connection/profile selection. Never clear an old owned auth tab because a new server/owner was selected. |

Relevant exact files: `background/connection.ts`, `connection/{gateway-session,core-api,project-context,active-recording}.ts`, `connection/session/writes.ts`, `connection/outbox/store.ts`, `connection/host-lease/session-ledger.ts`, `connection/in-flight/{index,record-area}.ts`, `background/saved-state.ts`, and `runtime/automation-tab.ts`. Bootstrap in `background/index.ts` currently overwrites the loaded client ID with a global ID; hosted install identity must instead come from the selected credential snapshot.

Wrap the existing Core `ClientGatewayStorageArea` by `lineageKey` for outbox, in-flight and lease storage; reuse Core reconciliation, do not copy it. A fresh PKCE token otherwise looks like a resume to Core's current token-bearing-hello lineage rule. Never relabel old unscoped messages as the new hosted owner. Quarantine unprovable legacy queue state rather than replay it.

Core `packages/client-gateway-websocket/src/outbox/outbox.ts::setLineage` already merges held loss into persisted loss and clears held state only after persistence succeeds. Use the old instance's awaited checkpoint before retiring it; retain a failed old checkpoint rather than silently dropping memory. `flush` reports binding-mismatch drops, but those are not automatically a loss marker. Existing reasons are only count limit, byte budget and write failure (`outbox/loss/reasons.ts`): do not mislabel an owner/privacy discard. Preserve old queue/loss in its quarantined scope, or add a separately briefed neutral Core discard-accounting API if deliberate deletion becomes necessary.

## Provider-free acceptance for those units

Author tests beside the subject. Use deferred fake browser/storage/fetch/socket ports and synthetic secrets; no accounts, production state or providers. Required assertions:

1. Loading/failing registry, private store denial, same-session hydration, ownership on blank/signup/external URLs, exact release, route update, committed plus pending URL and host/path lookalikes. Fully local never-used mode works with no session/identity API; uncertain active mode refuses.
