## Required corrections before a complete hosted path

**Identity must agree with actual hello.** Core's current `apps/web/src/server/connect/issue-credential.ts` deliberately sets gateway `clientId = clientInstallId`; the OAuth `client_id` remains the fixed application id `fluxiq-browser-extension`. The extension must persist an install id for the chosen Core origin and use that exact id as `session.clientId` in hello. Its bootstrap must stop replacing a hosted profile's id with the old global one. A random UUID with the existing `extension-` prefix fits the contract; no second key enrollment scheme is needed.

**Credentials must be bound to their destination.** The current `sessionTokenStorage.read` returns the global token without checking its saved `serverUrl`. Saving a new endpoint can therefore reuse the previous endpoint's token. `coreApiCredentials()` similarly combines the current HTTP URL with that same token. This is source-level evidence of a missing boundary, not a live exploitation claim.
Introduce a profile record keyed by canonical selected Core origin, with its own stable install id and pinned approved gateway URL, credential, connected-client id, expiry and safe user/workspace summaries. Select and persist a profile atomically. Socket reads/rotation writes and every HTTP bearer presentation must retain the profile binding they started under; switching the selected server cannot retarget a late write or send its credential to another server. Do not let discovery fetched for origin B carry A's credential.
Preserve existing local pairing through its current transport. Migration must not invent provenance: a legacy record remembers only the gateway URL, not its historical HTTP origin. Migrate only a binding established by the existing selected connection; a mismatched or unprovable credential stays unsent until reapproval. Do not silently delete legacy data or reset browser profiles to make migration pass.

**A new credential is a new trust context, not necessarily a resume.** The extension's outbox uses one global `fluxiq.outbox` in session storage. Core's existing `FluxIQClientGatewayConnection.onSessionReady` preserves stored lineage when the hello had a token and no pairing_required event. A fresh pre-socket PKCE token satisfies that condition, so simply replacing the token can carry the old profile/account's queue lineage forward. Adoption must choose a profile/user/workspace/trusted-client-bound outbox namespace and fresh session context, reset stale project/session ids, and prevent the previous owner's queue from flushing there. Preserve/report old queued data through the owning loss/retention contract; never silently replay it under a new owner. Keep Core's generic reconnect rules; correct the host's store binding and new-trust initialization.

**Sign-in tabs are control traffic.** `background/connection/active-page.ts` forwards full `tab.url` into state and status; `browser-state.ts` enumerates all tabs with URLs. Root listeners also forward navigation into recording. A done URL can contain a real authorization code in its fragment.
The coordinator must intercept its owned tab before generic handlers, and a shared control-tab filter must also cover `activeTab()`, `allTabs()`, state snapshots, recording/navigation intake and diagnostic/status exposure. Merely consuming the onUpdated event does not stop the next all-tabs heartbeat from leaking it. Preserve control-tab classification through worker recovery/cancellation until the tab leaves that protected flow or closes. No auth tab is an automation target or recording input.

Retain the known local pairing path, and never send a hosted user into the currently informational `/connect` page as if typed codes work.
Discovery is fetched without cookies from the chosen canonical origin, with bounded JSON, redirects refused or explicitly origin-validated, and `parseFluxIQDiscoveryDocument(document, chosenOrigin)`. A separately hosted gateway is a distinct credential destination to retain explicitly, not a reason to forward an old credential or request blanket host access.

## Proposed flow and transient lifetime

1. Only an own sidepanel/popup user action may start sign-in. Check/grant access to the chosen Core origin, fetch and validate discovery/capabilities, and read/create that origin's install id. Do not open an unauthenticated service socket to manufacture a pending pairing.
2. Use Web Crypto: independent 32 random bytes for verifier and state, unpadded base64url; S256 is SHA-256 of ASCII verifier. Use the existing contract schemas to validate the completed request. The client label comes from the existing `browserClientLabel` helper.
3. Store one attempt's origin, pinned endpoints, install id, state, verifier, phase and own tab id in trusted `chrome.storage.session`, never sync/local or page storage. Do not store a password or panel cookie anywhere; the normal tab handles sign-in. No raw code needs persistent storage.
4. Create an owned blank tab, persist its returned id, then navigate it to the authorize URL. This avoids a fast redirect arriving before `tabs.create()` resolves with an id. Register top-level listeners synchronously before asynchronous recovery. The background owns the attempt because Firefox's popup may close when the normal tab opens and Chrome may suspend its worker while the user signs in.
5. An update is eligible only for the exact stored tab id, exact configured origin, exact done path, empty query, valid fragment and constant-time/equivalent exact saved-state match. Ignore unrelated tabs and unrelated messages; reject a malformed or wrong-state completion from the owned tab. Never select a tab just because its URL contains a matching state. A postMessage bridge is unnecessary.
6. Serialize completion handling and durably mark the attempt `exchanging` before starting its one-use request, so duplicate URL events cannot exchange it again. POST the contract body to the pinned token URL with `credentials: "omit"`, JSON and `fluxiq-client: browser-extension`; do not follow an off-origin redirect. Parse the existing success/error schemas and return only safe fixed failure text/status to the panel.
7. Commit the credential and complete binding durably before adopting it in the existing gateway token-storage path, reconnecting or reporting success. Then clear verifier/state, close only the owned tab, and let the existing signed rotation/confirmation/reconnect path continue. Verify real session_ready before calling the socket connected.
8. Denial, tab closure, explicit cancellation, server selection change and unrecoverable malformed completion clear verifier/state. A deliberate new consent replaces the previous pending attempt; do not close unrelated tabs. Cancellation during an in-flight exchange must not adopt its later response into another selected profile; a known delivered credential can be revoked rather than abandoned silently.
9. Worker recovery in `waiting_redirect` validates the stored attempt and exact own tab before resuming observation. In `exchanging`, the request may already have committed: never resend the code or pretend no credential was minted. Clear sensitive state and require fresh consent unless a future durable delivery-receipt design proves recovery safe. A browser restart clears session storage; a persisted bound credential reconnects, an unfinished sign-in starts again.

The server code's 120-second expiry begins at consent, not when the extension opens the login tab. Do not add an arbitrary short login timeout that breaks account creation. Persisted attempt phase/tab closure provides lifecycle cleanup; standard code/session expiry remains authoritative. No background keep-alive socket or managed-host enrollment ticket should be introduced for this flow.

## Browser storage and permission evidence

Both current manifests already declare `tabs`, `storage`, `webNavigation`, scripting and `<all_urls>` host access. Chrome/Edge use a minimum Chrome 116 MV3 service worker and sidepanel; Firefox uses a minimum 128 background script and popup. Hosted PKCE needs none of `identity`, `cookies`, password access, webRequest or a new all-site permission. Chrome documents that tabs creation itself is unprivileged while URL observation requires the existing tabs/host access. [Chrome tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs).

Check the chosen origin with `permissions.contains`. If a browser/user has withheld it, request only that origin's match pattern from a direct user gesture using a declared permission. Existing broad automation access is separate from the narrow Core-origin need; do not add or request blanket access just to fetch discovery/token/revoke. Firefox 127+ exposes host permissions at install, but users can still grant/revoke them. [MDN host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions), [permission requests](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/permissions/request).

**API availability differs from enforced isolation.** Official Chrome docs mark `StorageArea.setAccessLevel` as Chrome 102+, but this alone does not prove the call isolates `local` on every supported version. The pinned Chromium 116 source restricts access checks to session storage and rejects setAccessLevel for ValueStore-backed areas, including local. Current Chromium has per-area support. Do not encode MDN's later all-area version number as independently verified product policy. [Official API](https://developer.chrome.com/docs/extensions/reference/api/storage/StorageArea), [Chromium 116 implementation](https://raw.githubusercontent.com/chromium/chromium/116.0.5845.96/extensions/browser/api/storage/storage_api.cc), [current implementation](https://raw.githubusercontent.com/chromium/chromium/main/extensions/browser/api/storage/storage_api.cc).

Firefox's compatibility data reports session storage from 115 and no setAccessLevel implementation. Session storage is privileged by default and clears at browser stop. This fits both declared minimums for pending PKCE. The existing optional, unawaited local.setAccessLevel call, plus a test that only checks its source text, does not establish cross-browser durable credential isolation. [MDN session semantics](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session), [MDN browser compatibility data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/storage.json).

Recommend one extension-origin IndexedDB repository for durable credentials and pending revocations, retaining ordinary nonsensitive settings/install ids separately as needed. Chrome documents extension-origin web storage as shared by its trusted extension pages/worker, while content scripts access the host page's web storage; IndexedDB is available in workers. Actual Firefox/Chrome/Edge isolation still needs a browser check. Merely detecting a method or resolving a mock Promise is not that proof. [Chrome extension storage model](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies).
No new unlimitedStorage permission is justified for a small credential repository. Store errors must prevent publication/activation; do not fall back to publicly exposed local/sync storage or silently downgrade a lasting credential to an undocumented lifetime.

Chrome and Edge store builds have different extension ids and need both exact extension Origins in Core's allowlist. Unpacked test ids must be configured explicitly for their isolated instance. Firefox install Origins are dynamic; the existing Core contract supports its controlled `moz-extension://*` rule. Microsoft lists the relevant Chromium-style APIs, but this is not a browser execution claim. [Edge API support](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/api-support).
