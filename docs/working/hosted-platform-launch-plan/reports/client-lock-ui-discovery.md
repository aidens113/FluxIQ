# Authenticated-client protocol and UI removal discovery

Outcome: Done (discovery only). Source remains frozen. No builds, tests, browser runs, server operations, paid calls, or git mutations were performed.

The user correction in Current State supersedes first-unlock and locked enrollment: a currently authenticated, approved client must be able to use its authorized configured keys immediately. Removing the form or banner alone does not meet that requirement. The entire snapshot/ticket/password/lift roundtrip below must disappear from the normal approved-client path. Backend custody replacement and historical key migration belong to the separate `authenticated-client-access.md` investigation.

**A real discrepancy to fix at the boundary**

Core web `apps/web/src/features/chat-widget/transport/models-port.ts` strips everything except kind/provider/enabled. Shared chat therefore treats its enabled keys as ready even when Core says `unlocked:false`. The extension's `background/automation-relay/automation-relay.ts` preserves `unlocked`/`lockedBecause`, so the same shared chat can show a lock there. This is loss of availability information in the web adapter, not evidence that the backend lock is absent. Both adapters must carry the same frozen safe status; removing more fields would hide the defect.

The existing readiness readers also infer readiness from *any enabled listed key*. A truthful capability read must concern the effective authorized model/provider selection, not an enabled custom secret or an incompatible provider. No live provider call is needed merely to display setup metadata.

**Proposed status semantics for the backend/wire owner to freeze**

These are meanings, not final exported type names. The backend investigator currently recommends metadata `availability: available | unavailable` with distinct legacy recovery, host protection, and invalid ciphertext causes; coordinate that representation before dispatching UI changes.

| Meaning | Evidence and display | Effect on work |
| --- | --- | --- |
| Authenticated client, available model capability | Current account/workspace/IAM and approved-client authority permit use; effective configured credential is retrievable. Say configured/ready without claiming the provider has validated it. | Model work may proceed under normal authorization. No additional unlock/password/PIN. |
| Missing or disabled/incompatible model configuration | Auth remains valid; no enabled compatible authorized model configuration exists for the requested work. Offer Add/configure model key. | Relevant when a model is actually needed. Deterministic replay and unrelated authenticated operations continue; no connection gate or client-lock banner. |
| Provider failure | An actual provider operation reports its real category, such as rejected credential, exhausted provider balance, throttling, or transport failure. | Show the sanitized actual failure/recovery action. Do not invent a password unlock or translate it into local sign-out. Preserve the runtime's existing retry and continuation policy. |
| Legacy recovery or host/ciphertext unavailability | Configuration exists but the server cannot retrieve it; distinguish recoverable historical seal, unavailable host protection, and invalid ciphertext as decided by backend. | Explain the actual operator/key-owner recovery. Never call it ready, missing, or client-auth revoked; never pretend a second password is inherently required for every approved client. Deterministic work remains usable when it does not need that key. |
| Revoked/expired/unauthenticated authority | Current authentication/approval/account/workspace permission is gone. Use existing HTTP 401/403 or gateway revocation/disconnect semantics. | Refuse the affected operation and require actual sign-in/reapproval where appropriate. Remove access consistently, not only the ability to decrypt while leaving the client apparently authorized. |
| Unknown/stale read | Offline transport, malformed response, unsupported peer version, or failed status fetch. | Claim neither ready nor missing. Use connection/read failure feedback; retain the last observation only with explicit stale semantics. |

Ordinary panel logout drops that panel's authority/custody; it must not half-disable a separate approved client. Explicit client revoke, administrative account/session policy, and credential compromise remain security boundaries. The backend must define those events precisely so UI can say what was revoked. Current user/workspace/domain permission checks still apply to every call. No policy here permits using another person's key or a stale approving session.

**Compatibility and rollout constraints**

- Snapshot fields are optional and UI ports currently use `unknown`, so a missing field already has different practical effects across adapters. Define a checked, safe shared status representation and explicit fallback. Old clients may ignore additive metadata, but new clients must not reinterpret an explicit old `unlocked:false` as ready. An incompatible old locked backend should be reported as unavailable/upgrade required, not offered the removed unlock ritual.
- Stopping new `model_key_locked` production is separate from deleting its parser alternative. `parseAutomationStudioTaskAttempt` currently rejects unknown waiting reasons. Keep legacy records decodable or migrate them through the owning persistence layer; do not hand-edit records. If new persisted reasons are introduced, update contracts, mirrored `ChatTaskAttempt` in `chat/ports/results.ts`, strict readers, runtime producers and fixtures together. A changed closed enum is not safely compatible merely because the JSON field is unchanged.
- `chat/ports/tests/results.test.ts` explicitly checks parity between restated UI records and contracts. Keep that boundary test. `secrets.locked` code/predicate and the `fluxiq/ui` copy exports are public; removing them abruptly breaks importers. Deprecation/read compatibility can remain while normal writers and UI operations are removed, but no retained export may re-enable default locking. The backend/wire owner chooses the version/capability policy before dispatch.
- Approval `{password,totp}` and `{session,unlocked}` are consumed by this web dialog and browser harness. Remove the route branch and UI/harness expectations coherently; an older caller sending unused fields must not accidentally trigger the old gating. `#unlock=` tickets and `lockedClients` have no purpose in the new approved-client flow. Remove all producers/consumers, not just the visible button.
- Gateway revoke/drain/proof rotation and token-reuse behavior remain their existing protocol. There is no identified reason to change the gateway protocol version solely to remove the model-key ceremony; any actual version bump follows the final changed wire contract, not this discovery's guess.
